## Premises that did not hold

- **read_thread_snapshot is not a transcript replay.** Upstream `readThreadSnapshot` fails with "Claude V2 adapter does not implement snapshots" and `canReadThreadSnapshot` is false. Turin keeps it failing. Only `rollbackThread` is ported, and it is cursor-based (`ClaudeAdapterV2.ts` 9362-9420, helper 1497-1540).
- **`inject_history` does not exist upstream.** Nothing in `upstream/apps/server` or `upstream/packages` names it. "History import" maps to `claudeHistoryWorker.ts` and `cli/claudeHistory.ts`, which only wrap SDK `getSessionMessages`/`forkSession` in an isolated process. Turin's `ClaudeAdapterV2::history`, `subagent_history`, `list_history` already do that in-process. The only upstream consumer in the adapter is subagent transcript reads (`ClaudeAdapterV2.ts` ~1007, workflow members). That work belongs to item A below.

## Remaining work, in order

### A. Subagent lifecycle (largest; nothing started)
Upstream `ClaudeAdapterV2.ts` (line numbers approximate, from the pinned checkout):
- Agent tool_use never becomes a tool call. It registers a pending launch (`rememberClaudeSubagentLaunch` 3188-3260) and is skipped with `continue` (~7500). Turin currently emits it as a DynamicTool item.
- Session subagent registry (`sessionSubagentsByTaskId`, `...ByToolUseId`, ~3598-3630) and `updateClaudeSubagentNode` (~4990-5340). It emits `subagent.updated` and creates child threads through `childThreadId` / `childRootNodeId`.
- `task_started` / `task_updated` / `task_progress` / `task_notification` handling (~6490-6800, ~7060-7230). Route subagent frames by `parent_tool_use_id` (6697-6725, 7224-7290). Agent tool_result terminalization (~7560-7590).
- `stopSubagent` (9244). Background roster `claudePendingBackgroundTask` / `parseClaudeBackgroundTaskEntry` (2052-2141), which feeds `pendingBackgroundTasks` on the provider thread.
- Replay targets: fixtures `subagent`, `claude_background_subagent_lifecycle`, `claude_background_subagent_after_root`, `claude_background_task_after_root`, `claude_background_task_wake`, `claude_background_task_interrupt`, `claude_local_bash_task`, `claude_subagent_resume_after_restart`, `claude_nested_subagent_model`.

**Known leak, existing before this work:** subagent frames (`parent_tool_use_id` set) still add tool calls and text to the parent turn. Routing them to child threads is part of A.

### B. Workflow progress (module exists, no callers)
`claude_workflow_progress.rs` is ported (merge, handles, phases, agents) but nothing calls it. Wire it into the Workflow/Agent result path after A exists. Upstream: `claudeWorkflowProgress.ts` (192 lines), `parseClaudeWorkflowRunHandles` use in the tool_result path (~7600-7650), and workflow member child threads (test ~12003). Fixtures: no Claude transcript covers Workflow yet (`subagent_v2*` are codex and muse), so the Claude coverage is the Workflow tests in `ClaudeAdapterV2.test.ts` (~11733-13700).

### C. Tool output parity (correctness, not just a title)
Upstream feeds tool items from the structured `tool_use_result` when a user message carries exactly one tool_result (`claudeToolResultEntriesFromMessage`, 2474-2500; `claudeNativeToolOutputFromStructuredResult`, 2172). It reads command output through `claudeCommandOutputText` (2204), which handles structured stdout/stderr. Turin uses only the `content` block for item output. Bash output can therefore differ from upstream.
- The structured value already feeds the task list (commit `ec5d495`), but item output does not.
- Also not ported: `viewedImagePath` (`isWorkspaceImagePreviewPath`), web search patterns and results (`webSearchPatternsFromClaudeTool` 2264, `webSearchResultsFromClaudeOutput` 2275, web fetch snippet 8000 chars).

### D. Streaming deltas
Reasoning and text stream through `stream_event` frames with a 50 ms `ProviderTextDeltaCoalescer` (upstream 5762-5830, 6927-6970, `ProviderTextDeltaCoalescer.ts`). Turin emits only completed blocks. Add the stream path, then switch `reasoning_item` to `streaming: true` updates.
- `claudeWritesUpdatesAsThinking` (1282-1290) is not ported. It treats a second thinking block before a tool call as the tool's update.

### E. Held frames and prompt echo
Upstream holds frames while a prompt echo is pending (`isClaudePromptEchoGatedFrame` 2707, `claudePromptLifecycle` 2749, `heldToolUseIds`). It defers ExitPlanMode and TodoWrite projections until the frame is released (`heldProposedPlansByToolUseId`, 3801; the defer branch at ~8228). Turin projects on arrival. This only matters with wake and background turns.

### F. Compaction context window
`maxTokens` on the post-compaction usage is `null`. Upstream resolves it with `resolveClaudeCatalogContextWindowTokens` (`ClaudeModelCatalog.ts` 287-296, which reads the `contextWindow` option). That belongs to T10d's catalog. Once the catalog exposes the resolver with a model selection, replace the `null` in `claude_provider_adapter.rs` `compaction()`.

### G. Wake turns and continuations (large)
`continuationRequests` (3443), wake-turn buffering and the single continuation run (~6244-7012 tests). The sink exists in provider-core (`provider_continuation_requests.rs`); the Claude side needs the wake-turn state machine.

### H. Goals (not on the task list; flagging)
`nextClaudeGoal` and `claudeGoal*` (1292-1345), native goal state on the provider thread.

Those are the next cheap wins for the fixture path, since they are single-process runs the current fake CLI can drive. Check `claude_mcp_tool_presentation` first, since it covers the MCP presentation path directly.

## Notes for whoever picks this up
- The fake CLI now appends each launch's argv to `FAKE_ARGV` (`dir/argv.log`). Use it to assert launch flags.
- Rollback and fork cause errors are `Protocol` errors carrying upstream's text. `ProviderAdapterErrorKind::RollbackThread` and `ForkThread` have no cause field. Changing provider-core's error kinds is a separate, small change.
- T3's own MCP exemption (`resolveT3McpToolDefinition`) is not ported because the T3 MCP servers are cut.
- Build contention: the machine ran about 80 cargo/rustc processes during this session. Runs can take ten minutes or more.
