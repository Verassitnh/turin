# T22a: live read path (app wiring, slice 1)

Branch `task/T22a-live-read`. Goal: `TURIN_DATA_DIR=<dir> cargo run -p turin`
shows the projects, threads and message history stored in Turin's own SQLite.

## Step 1: seam map (read-only)

### Upstream: what the web client subscribes to

| Client need | Upstream RPC / source | Payload |
|---|---|---|
| Shell (sidebar) | `subscribeOrchestrationV2Shell` (`apps/server/src/ws.ts:953`) | `OrchestrationV2ShellStreamItem`: `Snapshot{snapshot, resolvedRepositoryIdentityRoots}`, then `ProjectUpdated`/`ProjectRemoved`/`ThreadUpdated`/`ThreadRemoved` deltas, `Synchronized` marker |
| Shell snapshot body | `loadShellSnapshotParts` (`orchestration-v2/ShellStream.ts:43`) | one read transaction: `threadManagement.readShellSnapshot({location:"active"})` (decoded thread shells), `projects.listShells()`, `applicationEvents.latestApplicationSequence` |
| Shell deltas | application event log (`OrchestrationEventStore.streamApplicationEvents`) → per aggregate refetch (`getThreadShell`, `projects.getShell`) → `shellStreamItemFromThreadShell` | |
| Thread open | `subscribeOrchestrationV2Thread` (`ws.ts:~837`) | `Snapshot{snapshotSequence, projection, historyCursor?, hasMoreHistory?}`, then `Event{sequence, event}` after `snapshotSequence` (`EventSink::stream`), `Synchronized` marker |
| Bounded snapshot | `getThreadSnapshotWindow({rowLimit: 77, userTurnLimit: 10})` + `buildBoundedThreadStreamSnapshot` (`ThreadStream.ts:71`) | window of the newest 10 user turns; cursor from `selectRecentTimelineWindow` |
| Older history | `getThreadHistoryPage(threadId, cursor)` (RPC `orchestrationV2.getThreadHistoryPage`) | `{snapshotSequence, items, nextCursor, hasMoreHistory}` |
| Resume | `decideThreadResume` (replay ≤128 events / 1 MiB, else snapshot) | |

Client side: `packages/client-runtime/src/state/{shell,threads,orchestration}.ts`
drive the reducers. Web sends `acceptBoundedSnapshot: true` for threads.

Constants (`orchestration-v2/threadHistoryPaging.ts`): `maxUserTurns 10`,
`maxItems 75`, `OLDER_THREAD_USER_TURN_LIMIT 20`, row limit 77. Rust has the
same constants in `orchestration/src/projection/thread_history_paging.rs`.

Data dir (`apps/server/src/config.ts:135`): `stateDir = baseDir/userdata`,
`dbPath = stateDir/statev2.sqlite`. Turin uses `~/.turin` as its base and
keeps `statev2.sqlite` directly in it (PORTING.md, T3 import notes). See
step 2 for the resolver.

### Turin store: what it accepts

`crates/app/src/state/store.rs` (`spawn_client_state`):

- `ClientStateRuntime { sender, requests, handle }`.
- `ClientStateSender` (`state/events.rs`) takes `ClientStateEvent`s:
  - `shell(Vec<ShellStreamItem>)`: `Synchronized`, `Snapshot{snapshot: ShellSnapshot, resolved_repository_identity_roots}`, `Event(ShellStreamEvent::{ProjectUpdated, ProjectRemoved, ThreadUpdated, ThreadRemoved})`. `ShellStreamItem: From<OrchestrationV2ShellStreamItem>`.
  - `thread(thread_id, Vec<ThreadStreamItem>)`: `Synchronized`, `Snapshot{snapshot_sequence, projection: Arc<ThreadProjection>, history: Option<ThreadHistoryMeta>}`, `Event{sequence, event}`. `ThreadStreamItem: From<OrchestrationV2ThreadStreamItem>`.
  - `ThreadHistoryPage { thread_id, request_cursor, items: Vec<VisibleTurnItem>, meta }` and `ThreadHistoryFailed`, `ThreadFeed(FeedStatus)`, `ShellFeed(FeedStatus)`, `ScratchWorkspaceRoot`, optimistic-update variants (write path, out of scope).
- `ClientStateRequests` (mpsc receiver the adapter drains):
  - `OpenThread { thread_id, after_sequence }` → adapter must answer with `thread(...)` items.
  - `CloseThread(thread_id)` → adapter may stop that feed.
  - `LoadEarlier { thread_id, cursor }` → adapter answers with `ThreadHistoryPage` or `ThreadHistoryFailed`.
- `ClientStateHandle` (UI end): `snapshot()`, `open_thread`, `close_thread`, `load_earlier`.

### Persistence and projections

- `turin_persistence::Db`: `open(path)`, `open_configured(path)` (imports a sibling v1 DB, then opens), `open_in_memory()`, `write(|tx| …)`, `read(|conn| …)`. Migrations run on writer open (`finish_writer`).
- `OrchestrationEventStore` (`persistence/orchestration_event_store.rs`): `read_agent_events`, `read_application_events`, `latest_agent_sequence`, `latest_application_sequence`, `publish_committed`, `stream_application_events(after) -> EventSubscription` (replay + live, `ApplicationStoredEvent` items).
- `ProjectionStore` (`orchestration/projection/store/mod.rs`): `get_thread`, `get_thread_projection`, `get_thread_snapshot`, `get_thread_snapshot_window(opts)`, `read_shell_snapshot` (rows, one tx) → `ShellSnapshotRows::decode`, `get_shell_snapshot`, `get_thread_shell`, `get_thread_history_page(thread, cursor, through, conversation_only)`, `get_timeline_page`, `get_message_count`.
- `ProjectStore` (`projection/project_store.rs`): `get(id, include_deleted)`, `list(ids, include_deleted)`, `get_shell`, `list_shells`.
- Shell composition helpers (`projection/shell_stream.rs`): `build_active_shell_snapshot`, `shell_stream_items_from_initial_snapshot`, `shell_stream_item_from_thread_shell`, `to_shell_application_event`.
- Thread history helpers (`projection/thread_history_paging.rs`): `select_recent_timeline_window`, `select_history_page_from_cursor`, `encode_thread_history_cursor`, `THREAD_HISTORY_*` constants.

### Write side (orchestration pipeline)

- `EventSink::new(events, outbox, Arc<dyn ProjectionApplier>)`. Writes: `write(WriteInput)`, `commit_command(CommandCommit)`, `commit_project_command(ProjectCommit)`.
- `EventSink::stream(StreamOptions { thread_id, after_sequence, event_type })`: replay then live, per thread. This is the thread live feed.
- **Gap found:** no production `ProjectionApplier` exists. Only test doubles implement it. Every write would fail to fold into the read model. The seam in `projection/store/apply.rs` (`apply_event`), `ProjectStore::apply_in_tx`, and `turn_item_position_store::normalize_in_tx` are all ready. See step 4.
- Publish is after commit only. Live fan-out is in `EventSink`'s `LiveHub` (thread events) and `OrchestrationEventStore`'s hub (application events).

### Deviations (T22a, read path)

| Upstream | Turin | Why |
|---|---|---|
| `subscribeThread` sends a bounded snapshot for web clients only when `acceptBoundedSnapshot`; resume replays from the client cursor | Always a fresh bounded snapshot on open; `after_sequence` ignored | Replay is an optimisation. `decide_thread_resume` already falls back to a snapshot. |
| `buildBoundedThreadProjection` applies `windowBudget`, dependency reserve, and double-charges local row bytes in the bounded snapshot | Full read then `select_recent_timeline_window` with the full 1 MiB cap and single-count row bytes | Socket frame budgets are cut (PORTING.md). Without user turns the in-process window can be up to ~2× upstream. Next slice: port `projectedRowBoundedSnapshotEncodedBytes` or push the window into SQL |
| Bounded window also trims `messages`, `plans`, `contextHandoffs` (`messagesForBoundedProjection`, `active`/`pending` filters) | Only `visibleTurnItems` and `turnItems` are trimmed | Those filters are wire-size work for the cut transport. The store uses turn items for the timeline. Revisit with the bounded wire format |
| `ProjectEnrichmentService` resolves repository identity roots (`resolvedRepositoryIdentityRoots`) | Shell snapshot has `None` roots and `repository_identity: Some(None)` | Enrichment is a later slice (git/source-control) |
| Shell feed refetches per event, with `coalesce_shell_application_events` and `SkipUnchangedThreadShells` | Refetch per event, no coalescing | Correct first; coalescing when profiling shows it matters |
| `ProjectionStore::apply` runs under `Db::write`; upstream's applier is the `ProjectionStore` itself | `ProjectionWriter` delegates to the existing store functions | Same transaction, same rules. The wrapper is the seam the event sink already expects |

### Integration bugs found by the smoke and fixed

1. **Cursor `start_turn` blocked for the whole prompt** (`provider-cursor/src/session.rs`). The effect outbox runs one effect per thread at a time, so
   the running `provider-turn.start` starved `runtime-request.respond` and interrupt behind it: a Cursor approval could never be answered
   (Stop only appeared to work because cancelling the start effect dropped the prompt). `start_turn` now opens the turn (`begin_turn`) and
   spawns the prompt (`drive_turn`), like the other adapters; the outcome is the `finish_turn` terminal event.
2. **OpenCode events never reached the run** (`provider-opencode/src/adapter/{records,v1,v2}.rs`). Nodes, messages, turn items, plans and
   subagents were emitted with `runId: null`; upstream stamps `turn.runId` on all of them and the run executor routes by it. Every OpenCode turn
   ended `completed` with an empty reply. Each session now stamps the latest `start_turn`'s run on its events (`stamp_run`).
3. **OpenCode had no `ProviderDriver`**, so the `opencode` slot of `built_in_drivers` stayed empty and a configured instance was an
   unavailable shadow. `write/opencode_driver.rs` is the minimum: config (`enabled`, `binaryPath`, `serverUrl`, `serverPassword`), the real
   `OpenCodeAdapter`, the pending snapshot draft, no text generation. The live probe and inventory snapshot (`status.ts`) are not wired:
   settings/composer views show "checking" for OpenCode until that slice.
4. **Codex slot unfilled.** `providers.rs` now builds `CodexInstallation` (`ManifestCodexCompatibility`, `HttpReleaseDownloader`,
   `CommandRuntimeValidator`, under `<data dir>/codex`), a `FileSecretStore` under `<state dir>/secrets`, and fills the slot with
   `CodexDriver::with_managed_host`. Nothing is downloaded until a managed install is requested. The managed sign-in return URL is the
   placeholder `http://localhost:3773` (Turin runs no HTTP server).
5. T22b's `e2e_tests.rs` did not parse at the commit this branch started from (stray `)`); T22b fixed it in `e197bfd5`, merged here.
