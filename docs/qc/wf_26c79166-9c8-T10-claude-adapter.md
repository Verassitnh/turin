1. [medium] crates/provider-claude/src/claude_provider_adapter.rs:2280-2343 (finish_turn), also fail_active at :2396-2430. ## Confirmed findings (raw)

### [medium] Failed, interrupted, or cancelled turn never stops or cancels the running workflow subagents of its run
- `crates/provider-claude/src/claude_provider_adapter.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust finish_turn (line ~2280) only settles tool calls via finish_running_tools and emits the turn. No stop_task call or subagent cancellation happens on the non-completed path. stop_task is only reached from Command::StopTask (line ~865) and stop_subagent (line ~1126). Upstream upstream/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts lines ~5881-5910 (inside finalizeActiveTurn): `if (input.status !== "completed")` loops over sessionSubagentsByTaskId, skips anything not `subagent.task.workflow !== undefined && status === "running" && runId === this run`, calls `liveQuery.query.stopTask(taskId)` (15s, forked, best effort) and updateClaudeSubagentNode status failed or cancelled. The comment says a workflow left running where Lineage cannot see it is a bug.
- Fix: In finish_turn, when status is not Completed, iterate the subagent registry for running workflow tasks of this run_id. Send stop_task best effort off the terminal path (skip if the query is stopping or absent), and settle each to Failed for a failed turn or Cancelled otherwise, only if still running in this run. Mirror the upstream condition exactly.

### [low] stopSubagent on a subagent from an earlier CLI process is forwarded to the new process instead of failing at once
- `crates/provider-claude/src/claude_provider_adapter.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust stop_subagent (lines 1095-1131) checks only the state, the thread id, the requested-at timestamp, and whether self.claude is Some. It then calls claude.stop_task and waits up to 2s for the outcome. Rust has no earlier-process concept (grep for "earlier" finds none in the subagent or adapter code). Upstream ClaudeAdapterV2.ts ~9244-9262 returns ProviderAdapterProtocolError "Claude subagent has no live owning query with task stopping support." immediately when `existing.nativeThreadId !== nativeThreadId || existing.subagentsFromEarlierProcesses.has(subagent) || stopTask undefined`. A resumed subagent recovered after a process replacement therefore gets a stop sent to a process that never knew the task, then a 2s wait and a different "not confirmed" error.
- Fix: Track which subagents were registered by the current query process (the analogue of subagentsFromEarlierProcesses) and return the upstream "no live owning query" error before calling stop_task when the subagent belongs to an earlier process.

### [low] stopSubagent waiter returns the outcome even when the task was restarted during the wait
- `crates/provider-claude/src/claude_provider_adapter.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: resolve_stop_waiters (lines 1134-1141) sends Ok(Some(outcome)) to every waiter once confirmed_outcome(task_id) is Some. Upstream ClaudeAdapterV2.ts ~9302-9306 ends with `const current = sessionSubagentsByTaskId.get(nativeTaskId); return current?.task.startedAt === subagent.task.startedAt ? confirmedOutcome : undefined;`, so a Stop that raced a resume (new startedAt) gets undefined, not the new run's outcome. The Rust waiter has no startedAt comparison.
- Fix: Record the startedAt of the subagent when the Stop is sent. In resolve_stop_waiters, or when answering, return None if the registry's started_at differs from the recorded value.

### [low] Prompt-echo gate treats a frame with no parent_tool_use_id key as root output

### [low] Exit-before-result failure text depends on the order of two adapter events
- `crates/provider-claude/src/claude_adapter_v2.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: next_event (lines ~391-408) turns SessionEvent::Eof into 'Claude Code process exited before turn result' and SessionEvent::Exit into process_exit_message, both clearing pending_prompts. Whichever arrives first fails the turn, so the message is race-dependent. The test was loosened to accept either text (tests/session_replay.rs ~429-455, commit 219a867). Upstream has one exit path, finalizeActiveTurnAfterQueryExit (ClaudeAdapterV2.ts ~6198-6225), which fails the turn once with class transport_error and the squashed stream cause. The loosened assertion is justified by the race, but the message is still not deterministic in product code.
- Fix: Collapse Eof and Exit into a single exit event in the adapter (Exit carries the code or signal, Eof with no exit status becomes the same failure), so the message is fixed. Then restore the exact assertion.

### [low] Empty tool_use id panics the Claude actor task
- `crates/provider-claude/src/claude_provider_adapter.rs:` · dimension: robustness · upheld 2/2
- Evidence: claude_provider_adapter.rs:2667-2668 accepts any string: `let Some(native) = block.get("id").and_then(Value::as_str) else { continue; };` (no emptiness check). The id reaches `tool_call_artifacts` (claude_turn_items.rs:291-297), which builds `"nativeItemRef": native_ref(...)` with `"nativeId": ""` and calls `decode(json!({...}))`. `decode` (claude_turn_items.rs:55-59) is `serde_json::from_value(value).expect("Claude artifact matches the contract shape")`. The contract field `OrchestrationV2ProviderRef.native_id` is `Option<TrimmedNonEmptyString>` (contracts/src/orchestration_v2.rs:171), and `TrimmedNonEmptyString::deserialize` rejects "" (contracts/src/base_schemas.rs:184-188, 148-157). So an assistant frame with `tool_use` `id: ""` panics inside the actor task spawned at claude_provider_adapter.rs:436. The JoinHandle is never joined, so the session's event stream just ends and later commands fail with 'Claude session runtime closed'. The same path is reached from the subagent child-tool code at claude_subagents.rs:801-816. Upstream reports a schema failure for that item, not a crash.
- Fix: Skip tool_use blocks with an empty/whitespace id at claude_provider_adapter.rs:2667 and claude_subagents.rs:801 (use TrimmedNonEmptyString-style trimming, or `.filter(|id| !id.trim().is_empty())`), and/or replace the `decode` expect with a fallible decode that logs and drops the item, so malformed CLI frames cannot kill the session actor.

### [low] Actor serializes commands behind unbounded control-request awaits, with no interrupt timeout
- `crates/provider-claude/src/claude_provider_adapter.rs:` · dimension: robustness · upheld 2/2
- Evidence: run() (claude_provider_adapter.rs:794-823) awaits each command inline: `Action::Command(Some(command)) => self.command(command).await`. Inside command(), these await control requests with no timeout: interrupt at :1179-1183 (`.interrupt().await`, reached via Command::Interrupt at :854-855), set_model at :946, stop_task at :1126 and :865. The protocol's control path has no timeout either: claude-protocol/src/session.rs:300-309 is `rx.await.context(...)` when no cancel token is given. If the CLI stops answering one control_request, the actor is blocked and every later Interrupt, StopTask, StopSubagent, close_live and fork queues behind it. Upstream bounds this: ClaudeAdapterV2.ts:8966-8974 waits `Deferred.await(existing.closed).pipe(Effect.timeoutOption("10 seconds"))` and logs `orchestration-v2.claude-query-interrupt-timeout` before proceeding, and ClaudeAdapterV2.ts:9083-9089 applies the same 10 s bound before fork. Upstream runs these in separate fibers, so a hung control request does not block other commands.
- Fix: Bound the awaited control requests in the actor (for example `tokio::time::timeout(Duration::from_secs(10), …)` around interrupt/stop_task/set_model, mirroring upstream's 10 s), or run control requests in a spawned task that reports back through the command channel so the event loop keeps draining. On timeout, follow upstream: log, then treat the query as closing (drop/kill it).

### [low] Synchronous filesystem walk runs inside async workspace probes

They are reached from `pub async fn probe_claude_workspace_snapshot` (claude_provider.rs:657, call at :682 `discover_claude_skills(settings, Some(cwd), …)`) and from `pub async fn check_claude_provider_status` (claude_provider.rs:371, call at :490). ### [low] Dropping the session runtime SIGKILLs the CLI instead of closing it gracefully
- `crates/provider-claude/src/claude_provider_adapter.rs:` · dimension: robustness · upheld 1/2
- Evidence: impl Drop for ClaudeSessionRuntime (claude_provider_adapter.rs:463-468) only calls `handle.abort()`. The actor is dropped mid-await, so its `ClaudeAdapterV2`/`ClaudeSession` is dropped and `impl Drop for ClaudeSession` (crates/claude-protocol/src/session.rs:451-455) sends SIGKILL to the process group without waiting for exit. The graceful `claude.close()` at run() (claude_provider_adapter.rs:819-821) is effectively unreachable, because the runtime drops its command sender only after Drop has aborted the actor. The Rust code's own comment (claude_adapter_v2.rs:457-458, fork) says buffered transcript writes must be flushed by closing the CLI first. Upstream's close does `Queue.shutdown(promptQueue)` plus `closeClaudeQuery` (ClaudeAdapterV2.ts:938-944), and closeSession awaits the runner's completion (ClaudeAdapterV2.ts:9058-9070).
- Fix: On runtime drop, spawn a detached `close()` (`ClaudeAdapterV2::close` → `ClaudeSession::shutdown`, which already implements TERM/KILL escalation) that owns the session, instead of aborting the actor and relying on SIGKILL. Alternatively add an explicit async close on the session runtime, awaited by the orchestrator, that mirrors upstream.

### [low] Whitespace-only goal objective panics via expect
- `crates/provider-claude/src/claude_goal.rs:` · dimension: robustness · upheld 2/2
- Evidence: GOAL_ACTIVE regex at claude_goal.rs:23-25 is `^Goal active: ([\s\S]+?) \((?:not yet evaluated|(\d+) turns?)\)`. Text "Goal active:   (not yet evaluated)" (three spaces) yields capture " ", which is not trimmed. `goal()` (claude_goal.rs:40-51) then calls `serde_json::from_value(...).expect("goal matches the contract shape")`. `objective` is a TrimmedNonEmptyString, and `TrimmedNonEmptyString::new(" ")` fails (base_schemas.rs:148-157), so the actor panics at claude_goal.rs:113 (`None => goal(objective, …)`). The `Goal set:` branch guards with `!objective.is_empty()` (claude_goal.rs:94-96), but the `Goal active:` branch has no equivalent guard. Upstream ClaudeAdapterV2.ts:1293-1313 has the same regex and no trim, but it fails through Effect's schema, not a process-wide panic.
- Fix: Treat a blank captured objective as no match: `let objective = active.get(1)?.as_str(); if objective.trim().is_empty() { return None; }` (or use `TrimmedNonEmptyString::new(objective).ok()?`) before calling `goal()`, and drop the `expect` in `goal()` in favour of a fallible constructor.
