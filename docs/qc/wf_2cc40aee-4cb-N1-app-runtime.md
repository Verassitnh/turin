### [medium] Retired github/bitbucket keys are deleted when the secret copy fails but the file is rewritten anyway
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/N1-app-runtime/crates/runtime/src/server_settings/service.rs:606` · dimension: safety · upheld 2/2
- Evidence: service.rs:563-564 says "A failed copy retries on the next load". But service.rs:586-592 sets has_legacy_source_control = trusted && copy_ok && (...). On copy failure it clears secret_moves and leaves `value` without the legacy github/bitbucket hosts. Lines 606-610 then write `migrated` (typed ServerSettings, which has no github/bitbucket field) when `(trusted && legacy_providers.is_some())` or when `migrated_value != loaded`. `loaded` is captured at line 558, before fold_legacy_project_settings at 560, so a project-row fold also forces the write. The result: the file loses the `github` object with its `tokens` placeholder and the `hosts` account pin, while the secret stays under the legacy name `github-token-<hash>` with no reference. On the next load legacy_sc.github is None, so nothing retries and the token is effectively lost from the app. Test tests.rs:2120 (retired_github_keys_stay_for_another_load_when_a_token_cannot_be_copied) only covers a github-only file, where no write happens, so the gap is not tested. Upstream serverSettings.ts:813-849 has the same shape (migrated = folded without the legacy hosts, rewritten on `settingsFileTrusted && legacyProviders !== undefined`), so this is inherited, but the code comment is false for this path.
- Fix: Do not rewrite the file while a legacy source-control copy has failed. Either skip the write when legacy_sc is present and !copy_ok, or re-insert the raw retired github/bitbucket objects into the serialized JSON. Add a test with providers (or project rows) present plus a failing ReadFailing copy that asserts the github key survives. Record the change in the PORTING Deviations table, since upstream does this too.

### [low] Secret copy is followed by removal of the source with no fsync on the copy
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/N1-app-runtime/crates/provider-core/src/credential_store.rs:223` · dimension: safety · upheld 2/2
- Evidence: FileSecretStore::set (credential_store.rs:219-226) does tokio::fs::write(&temp, value), set_mode, then rename, with no sync_all. The legacy migration then depends on that copy being durable before it removes the source: service.rs:571-585 copies via secrets.set, service.rs:610 writes the settings file (write_file_string_atomically at support/atomic_write.rs:33-34 also has no fsync), and service.rs:611-613 unlinks the legacy secret. A power loss can persist the unlink and the rename metadata while the new file's data is still unflushed, leaving a zero-length secret and no legacy copy. The author already syncs in create_new_file (credential_store.rs:489, `file.sync_all()`), so the set path is inconsistent with it. Upstream ServerSecretStore.ts:204-206 has the same gap in set, though its create() does `file.sync` (ServerSecretStore.ts:236).
- Fix: Call sync_all on the temp file before the rename in FileSecretStore::set, and fsync the settings temp file in write_file_string_atomically before rename. Only then unlink the legacy secret. Note the deviation in the PORTING table.
