## Lead report

1. [low] crates/usage/src/usage_limit_sources.rs:259-283 (run_background). Problem: the select! loop builds a fresh 5-minute sleep each iteration, so any settings publish (even one that leaves usage_limit_sources unchanged) restarts the health cadence. Also, `changed()` returning Err at lines 268-270 breaks the whole loop, so the periodic refresh stops permanently if the settings sender is dropped. Upstream runs the interval and the settings stream as independent fibers. Fix: keep one interval outside the select (a pinned sleep re-armed only after a tick, or tokio::time::interval with the immediate first tick skipped). On Err, disable only the settings arm and keep the timer running. Add a PORTING.md Deviations note if the watch-channel behaviour is kept.

2. [low] crates/usage/src/cliproxy_api.rs:587-606 (parse_millis; used by credits() at ~334-340 and reset_credits() nextExpiresAt at ~599). Problem: expires_at is parsed as RFC 3339 only. Upstream uses Date.parse for the filter and sort, which also accepts date-only and no-offset strings, so availableCount and nextCreditId can differ. Fix: use js::date_parse_ms (crates/provider-core/src/js.rs:77) for the filter and sort. Do not switch nextExpiresAt to it, because upstream formats that value via DateTime.makeUnsafe and reads no-offset input as UTC. Trigger is hypothetical (the hub normally emits RFC 3339 with an offset), so this is low.

3. [low] crates/usage/src/cliproxy_api.rs:270 (auth_files), :311 (api_call), consume() ~513-516 and decode at ~544. Problem: a malformed auth-files or api-call envelope during consume reports "The hub management request failed." Upstream wraps all of consume in mapError and reports "The hub returned an unexpected reset-credit response." for any non-UsageLimitSourceError. Fix: in consume(), map non-UsageLimitSourceError failures to the reset-credit detail string, and keep the management-transport detail for transport errors only. Add a test with a malformed envelope.

4. [low] crates/usage/src/usage_service.rs:1194-1211 (read_summary spawn). Problem: inflight.remove(&key) and sender.send run only on normal completion, with no drop guard. If scan_summary panics, the key stays in inflight and every later identical read gets scan_failed("The usage scan ended without a result.") until restart. Upstream uses Effect.onExit, which also runs on defects. No panic is reachable on the current production path (the parsers are test-only so far), so this is latent. Fix: move the inflight removal into a Drop guard that also drops the sender. Add a test where scan_summary panics and assert that the next identical read starts a fresh scan.

5. [low] crates/usage/src/cliproxy_api.rs:288-294 (apiCall header). Problem: `if let Some(account_id) = ...chatgpt_account_id` inserts Chatgpt-Account-Id even when the value is "". Upstream's JS truthy check omits it. Fix: `.filter(|id| !id.is_empty())` before inserting. This matches the file's existing workspace_id handling at ~359.

6. [low] crates/usage/src/usage_scan_cache.rs:302-316 (decode validation). Problem: gh is rejected unless it is a safe non-negative integer at most u32::MAX (upstream accepts any finite number). A missing cs becomes Null and is kept (upstream drops it for stateful formats). Totals are unaffected, because a dropped or Null-state entry falls back to a full re-parse, and Turin always writes gh and cs. Fix if matching is required: accept any finite gh, and treat a missing cs as invalid for stateful formats. Otherwise add a PORTING.md Deviations row. Also fix the stale module comment at usage_scan_cache.rs:14-15 ("every persist re-encodes the whole cache"), which contradicts the memoised fragments.

7. [low] crates/usage/src/usage_aggregation.rs:437-439 (round_usd). Problem: f64::round rounds negative exact half-micro-dollar ties away from zero, while JS Math.round rounds toward +infinity. Example: -2.5e-6 gives -3e-6 in Rust and -2e-6 in JS. Reachable only with a negative reported cost or a fast multiplier below 1, and only on exact ties. Fix: implement JS semantics exactly, `let f = x.floor(); if x - f >= 0.5 { f + 1.0 } else { f }`, or log the deviation. Note that `(x + 0.5).floor()` is not exact (it gives 1 for 0.49999999999999994, where JS gives 0).

8. [low] crates/usage/src/usage_service.rs:658-679 (persist_caches). Problem: the parking_lot state lock is held while cache_writer.write (669-671) JSON-encodes the whole file cache on a tokio worker, which stalls readers at 713, ~849 and ~1050. Upstream does the same synchronously, and fragments are memoised, so the cost is milliseconds at real sizes. Fix (optional hardening): snapshot under the lock, then encode and write inside spawn_blocking, keeping persist_lock for write ordering.

9. [low] crates/usage/src/usage_service.rs:713-735 (read_file_records). Problem: the state lock is held while cloning cached records. The warm-hit path (716-727) clones all records of every unchanged file on every scan, which is the main cost. The grown-file path (733, `cached => cached.cloned()`) clones the full CachedFile, but only size, provider and position are needed there. Fix: store records as Arc<[UsageRecord]> so clones are refcount bumps, and copy only the needed fields on the grow path. Performance only, not a totals defect.

Verdict: PASS (no critical or high findings; all 9 items are low severity).

## Confirmed findings (raw)

### [low] Chatgpt-Account-Id header sent with an empty value; upstream omits it
- `crates/usage/src/cliproxy_api.rs:293` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust: `if let Some(account_id) = account.id_token.as_ref().and_then(|token| token.chatgpt_account_id.as_ref()) { header["Chatgpt-Account-Id"] = json!(account_id); }`. Upstream cliproxyApi.ts apiCall: `...(account.id_token?.chatgpt_account_id ? { "Chatgpt-Account-Id": account.id_token.chatgpt_account_id } : {})`. The JS truthy check drops ""; the Rust Some() check keeps it, so a codex account with chatgpt_account_id "" sends the header with an empty value.
- Fix: Filter the Option on non-empty before inserting the header, e.g. `.filter(|id| !id.is_empty())`, to match the JS truthy test.

### [low] Health-check refresh timer restarts on every settings change, so unrelated edits postpone refresh
- `crates/usage/src/usage_limit_sources.rs:264` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust: `loop { tokio::select! { _ = tokio::time::sleep(DEFAULT_PROVIDER_HEALTH_REFRESH_INTERVAL) => { service.refresh().await; } changed = settings.changed() => { ... if next != last_sources { ...refresh } } } }`. A fresh sleep is created each iteration, so any settings change (even one that leaves usage_limit_sources unchanged) cancels the pending sleep and restarts the 5 minute interval. Upstream UsageLimitSources.ts runs the interval in its own forever-fiber (`Effect.forever(interval -> sleep -> refresh)`) and the settings stream in a separate fiber, so the tick cadence is independent of settings edits.
- Fix: Keep one interval outside the select loop (tokio::time::interval, or a pinned sleep that is only reset after a tick), so settings changes do not reset the health-check cadence.

### [low] Consume path maps auth-files and api-call decode failures to the wrong detail string
- `crates/usage/src/cliproxy_api.rs:270` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust auth_files: `serde_json::from_value::<AuthFiles>(response).map(|files| files.files).map_err(|_| source_error("The hub management request failed."))`; consume() calls `self.auth_files(config).await?` (line ~513). Upstream cliproxyApi.ts consume wraps the whole operation with `Effect.mapError((error) => isUsageLimitSourceError(error) ? error : new UsageLimitSourceError({ detail: "The hub returned an unexpected reset-credit response." }))`, and authFiles/apiCall decode ParseErrors are not converted to the management-failure detail inside consume. So a malformed auth-files or api-call envelope during redemption reports "The hub management request failed." in Turin but "The hub returned an unexpected reset-credit response." upstream.
- Fix: Keep decode failures as a distinct error from management transport failures, and in consume() map non-UsageLimitSourceError failures to "The hub returned an unexpected reset-credit response." as upstream does.

### [low] Scan cache decode validation differs from upstream for gh and missing cs
- `crates/usage/src/usage_scan_cache.rs:311` · dimension: logic-fidelity · upheld 1/2
- Evidence: Rust: `guard_hash > u64::from(u32::MAX)` plus `safe_integer(entry.get("gh"))` (rejects negative and fractional values), and `let saved_state = entry.get("cs").cloned().unwrap_or(Value::Null);` (line 315, so a missing cs is accepted as null for stateful formats). Upstream usageScanCache.ts decodeScanCache only requires `typeof entry.gh === "number" && Number.isFinite(entry.gh)`, and for stateful formats isValidState(undefined) is false, so a missing cs drops the entry. The two sides keep or drop different corrupt entries. Totals stay the same because a dropped entry cold re-parses, but the validation set does not match the upstream spec.
- Fix: Mirror the upstream checks: accept any finite gh, and treat a missing cs as invalid for stateful formats (only an explicit null is accepted).

### [low] round_usd rounds half away from zero; JS Math.round rounds half toward +infinity
- `crates/usage/src/usage_aggregation.rs:438` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust: `fn round_usd(value: f64) -> f64 { (value * 1e6).round() / 1e6 }`. Upstream usageAggregation.ts: `function roundUsd(value: number): number { return Math.round(value * 1e6) / 1e6; }`. For a negative exact half at micro-dollar scale, Math.round(-0.5) is -0 while Rust (-0.5).round() is -1.0, so a negative speedPremiumUsd or fast/ultrafast figure can round to a different value. Only negative values exactly on a .5 micro-dollar boundary are affected, so this is unlikely in practice.
- Fix: Use `((value * 1e6) + 0.5).floor() / 1e6` to match Math.round's tie-breaking, or document the deviation in the Deviations table.

### [low] Credit expiry parsed as RFC 3339 only; upstream uses Date.parse, which is more lenient
- `crates/usage/src/cliproxy_api.rs:587` · dimension: logic-fidelity · upheld 1/2
- Evidence: Rust: `fn parse_millis(text: &str) -> Option<i64> { DateTime::parse_from_rfc3339(text).ok().map(|parsed| parsed.timestamp_millis()) }`, used by credits() to filter `expires > now` and to sort. Upstream cliproxyApi.ts credits(): `Date.parse(credit.expires_at) > now` and `.toSorted((a, b) => Date.parse(a.expires_at) - Date.parse(b.expires_at))`. Date.parse also accepts date-only and no-offset date-time strings (the no-offset form is read as local time), and PORTING.md (manifest/usage timestamp row) already names js::date_parse_ms as the shared equivalent. An expires_at in one of those forms is dropped in Rust and counted upstream, which changes availableCount and nextCreditId.
- Fix: Parse expires_at with the shared js::date_parse_ms helper (the one PORTING.md describes), not RFC 3339 only, so the filter and sort match Date.parse.

### [low] In-flight scan entry is never cleared if the scan task panics, so identical reads fail until restart
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/N4s-usage-service/crates/usage/src/usage_service.rs:1205` · dimension: safety · upheld 2/2
- Evidence: read_summary spawns `let result = service.scan_summary(&input, &settings).await; service.inner.inflight.lock().remove(&key); ... let _ = sender.send(Some(result));` (lines 1205-1211) with no drop guard. If scan_summary panics (a provider parse_line or aggregator invariant), the spawned task unwinds: the key is never removed from `inflight` and the sender is dropped. Every later read with the same key clones the dead receiver, and tokio `watch::Receiver::wait_for` returns Err once the sender is closed without a matching value (tokio-1.53.3 src/sync/watch.rs:896-930), so each call returns scan_failed("The usage scan ended without a result.") until the process restarts. Upstream's Deferred/forkDetach has no such stuck state.
- Fix: Remove the inflight entry from a drop guard (or a scopeguard/Drop struct that also drops the sender) so it runs on panic as well as on normal completion, e.g. wrap the spawned future in a guard whose Drop calls `inflight.lock().remove(&key)`, or catch the panic with `catch_unwind`/`JoinHandle` and clear the entry on Err. Add a test where scan_summary panics and assert the next identical read starts a fresh scan.

### [low] Whole scan cache is JSON-encoded under the global sync state lock on an async worker
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/N4s-usage-service/crates/usage/src/usage_service.rs:661` · dimension: safety · upheld 2/2
- Evidence: persist_caches (async fn, runs inside tokio::spawn) does `let mut state = self.inner.state.lock();` (parking_lot Mutex, line 661) and then, still holding it, `self.inner.cache_writer.lock().write(&state.file_cache, &extra)` (lines 669-671). ScanCacheWriter::write (usage_scan_cache.rs:196-220) clones every cached fragment String, builds files via format!/join, and copies the whole document again, so the cost is proportional to the full 90-day cache. Meanwhile read_file_records (line 713), scan_summary (line ~1050) and scan_transcript_dir (line 849) take the same `state` lock on tokio workers, so they stall for the whole encode. The write itself is correctly moved to spawn_blocking, but the encode is not.
- Fix: Take a cheap snapshot under the lock (clone the ScanCache or swap it out, plus the source table and dirty flag), drop the lock, then run the encode inside spawn_blocking together with the write (keeping persist_lock to order writes). Keep the cache_writer mutex but move it into the blocking closure.

### [low] Cached transcript entry is cloned under the sync state lock on the async read path
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/N4s-usage-service/crates/usage/src/usage_service.rs:733` · dimension: safety · upheld 2/2
- Evidence: read_file_records takes `let state = self.inner.state.lock();` (line 713) and inside that block either builds the warm-hit records with `.cloned()` (lines 716-723) or returns `cached => cached.cloned()` (line 733), which clones the whole CachedFile (every record, tail record and resume state) while the parking_lot lock is held. For a file that grew, this is the entire cached record set. The lock is not held across an .await, so this is not a deadlock, but it blocks other tasks on the same worker threads for time proportional to file size.
- Fix: Clone the Arc-able data outside the lock, or store records behind Arc<[UsageRecord]> in CachedFile so a clone is a refcount bump; then only the cheap Arc clone happens under the lock.

### [low] Usage-limit health poll stops permanently when the settings watch sender is dropped
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/N4s-usage-service/crates/usage/src/usage_limit_sources.rs:269` · dimension: safety · upheld 2/2
- Evidence: run_background's select! has `changed = settings.changed() => { if changed.is_err() { break; } ... }` (lines 268-270). tokio's `watch::Receiver::changed` returns Err once the Sender is dropped, so the loop exits and the `sleep(DEFAULT_PROVIDER_HEALTH_REFRESH_INTERVAL)` arm never runs again. Upstream UsageLimitSources.ts:157-170 runs the interval as an independent Effect.forever fiber, separate from the settings stream (`Stream.runForEach`, lines 142-148), so the periodic refresh keeps going if the settings stream ends.
- Fix: When changed() errors, stop only the settings-watch branch (e.g. set a flag and select only on the sleep), and keep the interval loop running, matching upstream's two independent fibers.
