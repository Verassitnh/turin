## Lead report

1. HIGH, crates/orchestration/src/reactors/pull_request_sync/sweep.rs:362-364 (retry path around :369-375). A non-rate-limit `host.stack` error maps to `Some(None)`, which is the same value as "no stack". The sweep then clears the retry flag, records cadence, and dispatches a link sync with `stack: None`, which wipes the stored stack. Upstream PullRequestSyncReactor.ts:321-323 maps the failure to null, and :327-330 add the key to `retryStacks` and return with no write. Fix: keep a distinct failure state. On a non-rate-limit error, call `set_retry(key, true)` and return from `read_group` before `record_sync` and `sync_entry`. Port the upstream test "retries a failed stack read after the summary becomes terminal" (PullRequestSyncReactor.test.ts:390) with a fallible FakeHost.stack. The verifiers rated this medium, but the lead rated it high and it destroys stored state, so it is kept at high.

## Confirmed findings (raw)

### [medium] Thread PR discovery never matches a detected branch PR, so no thread PR link is ever recorded
- `crates/orchestration/src/reactors/thread_pull_request.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust line 465: `if let Some(pull_request) = &detected && !pull_request_matches_project(pull_request, project)` uses `project` from `ProjectShells::list()` (ProjectStore::list_shells). crates/orchestration/src/projection/project_store.rs:292 builds every shell with `repository_identity: Some(None)`, so `pull_request_matches_project` (lines ~86-96) always returns false and discover_group_checked calls finish_backfill and returns before any update. Upstream instead resolves identity first: ThreadPullRequestService.ts:79 `project: { ...project, repositoryIdentity }` from resolveProjectForPullRequestDiscovery, then line 212 `pullRequestMatchesProject(detected, resolvedProject)`. Upstream's own test ThreadPullRequestService.test.ts:32 'discovers a repository from a project shell without enrichment' asserts exactly this case (shell with repositoryIdentity null must still resolve). The Rust tests (thread_pull_request/tests.rs) cover only pure helpers and the handoff admits discovery integration is untested.
- Fix: Build a resolved project (`project.clone()` with `repository_identity = Some(identity)` from `self.identities.resolve(...)`) in discover_group_checked and pass that to pull_request_matches_project at line 465, as upstream does; add the upstream 'without enrichment' test as a Rust test.

### [high] Non-rate-limited stack read failure is persisted as 'no stack' instead of retried
- `crates/orchestration/src/reactors/pull_request_sync/sweep.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust lines 362-364: `Err(error) => { tracing::warn!(key, error = %error, "pull request stack lookup failed"); Some(None) }`, then the sweep records cadence (record_sync), clears retry (set_retry(key,false)) and runs sync_entry with stack None, so a link with a stored stack gets `changed = true` and a thread.pull-request-link.sync dispatch that clears the stack. Upstream PullRequestSyncReactor.ts:321-323 maps the same failure to `Effect.logWarning(...).pipe(Effect.as(null))` (fetchedStack = null), and lines 327-330 do `if (fetchedStack === null) { retryStacks.add(key); return; }` so nothing is written and the key is retried on the next sweep. The upstream test 'retries a failed stack read after the summary becomes terminal' (PullRequestSyncReactor.test.ts:390) is not ported; the Rust sweep tests have no stack-failure case.
- Fix: On a non-rate-limit stack error, set retry for the key and return from read_group before record_sync/sync_entry (return Ok(()) without recording), mirroring upstream lines 327-330; port the upstream retry test.

### [low] Watch reactor aborts a group's remaining targets on one failed dispatch and skips the quiet-reread reset
- `crates/orchestration/src/reactors/pull_request_watch_reactor.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust lines 772 and 779 inside `for target in &group.targets` (line 747): `self.record(target, next, Some(wake)).await?;` and `self.record(target, Some(report.next.clone()), None).await?;`. A failure returns Err from read_group immediately, so later targets in the group never get their wake/watch update, and `last_reads` is not cleared, so the failed target waits for the 10-30 min quiet reread. Upstream PullRequestWatchReactor.ts:425-437 (`eachTarget`) runs each target independently: 'Runs one thread's step for each thread in a group, so one refusal does not skip the rest', and its catchCause calls `lastReads.delete(group.key)` with the comment 'A thread that did not get its update must not wait for the quiet reread.'
- Fix: Run each target's record in a per-target match that logs the error, sets a failure flag, and continues; on any failure call `self.last_reads.lock().remove(&group.key)` as upstream does, then return Ok.

### [low] Blocking std::fs calls on the async checkpoint capture path, held under the workspace lock
- `crates/git/src/git_vcs_driver.rs:` · dimension: robustness · upheld 1/2
- Evidence: try_reuse_index (async fn, line 964) runs on every capture where HEAD exists (call site line 824) and does blocking std IO on a tokio worker: `std::fs::metadata(source)` (980), `std::fs::copy(source, temp_index)` of the whole .git/index (993), `std::fs::File::options().open(...)` plus `file.set_times(...)` (1003-1011). Capture runs inside CheckpointService's per-cwd lock (checkpoint_service.rs capture, _guard held across the git calls). PORTING.md 'Async-first (user rule)' requires filesystem work to run on tokio. Restore also has blocking std::fs::create_dir_all and read_dir in async fns (around lines 469, 487, 504). Note: this file is T06 code, not T13d-authored, but it sits on the T13d checkpoint round trip.
- Fix: Use tokio::fs::metadata and tokio::fs::copy, and run the set_times step through tokio::task::spawn_blocking (or tokio::fs::File with filetime). Keep the existing unwrap_or(false) fallback semantics. Apply the same change to the create_dir_all and read_dir calls in restore_checkpoint.
