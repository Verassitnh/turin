## Lead report

1. MEDIUM, crates/persistence/src/t3_import/snapshot.rs:80. `StepResult::More => pauses = 0` is the only counter in the backup loop (lines 73-100). SQLite restarts the backup from page 1 when the live source is written during the copy, and returns OK, so nothing bounds the loop. Reproduced: a writer committing every 5 ms kept the copy from finishing in 60 s. Fix: bound total restarts or wall-clock time, using backup.progress() (remaining/pagecount) and not resetting the counter on More. Sleep briefly on More. Fail through the existing busy_err path. Log the bound as a Deviation if kept.

2. LOW, crates/persistence/src/t3_import/snapshot.rs:156-158, reached via mod.rs:65-68 (plan) and mod.rs:72-75 (migrate_and_verify). Both public functions accept any path, open it with Connection::open (READ_WRITE|CREATE), and migrate it in place. Passing the live T3 file would write to it, and a missing path gets created. No current caller does this, so it is latent. This contradicts the never-open-read-write rule in PORTING.md. Fix: plan() opens with SQLITE_OPEN_READ_ONLY. migrate_and_verify takes &T3Snapshot or becomes pub(crate). Keep read-write only for the internal copy (adopt.rs:37, verify.rs:144).

3. LOW, crates/persistence/src/t3_import/snapshot.rs:37 (also adopt.rs:46 and adopt.rs:67-70). Work directories use default permissions (0755 at umask 022) and SQLite creates the copy as 0644, so a full copy of the user's T3 database is world-readable in /tmp for the copy and migration window. The hard-linked destination inherits 0644. Fix: create the snapshot and WorkDir directories with mode 0700 (tempfile Builder::permissions, DirBuilder mode). Create the copy as 0600. Decide consciously whether the hard-linked destination should be 0600 or match Turin's own DB creation, and log the choice in Deviations.

4. LOW, crates/persistence/src/t3_import/snapshot.rs:25-27 (T3Snapshot `_dir`) and adopt.rs:74-78 (WorkDir::drop). Cleanup is Drop-only, so SIGKILL, abort, or power loss leaves the full database copy behind, and nothing sweeps stale turin-t3-import-* or .t3-import-* entries. Fix: remove stale entries before a new import, or use a fixed work-dir name cleaned at startup. Apply the item 3 permissions as well.

5. LOW, crates/persistence/src/t3_import/plan.rs:77-94 (missing-id refusal) and plan.rs:52-69 (name mismatch). Ids below FIRST_V2_MIGRATION_ID (55) are refused, but upstream Migrations.ts:194 exempts them and only warns. Turin's own runner mirrors the exemption at migrations.rs:71. A ledger missing id 17, or with a renamed id 5, fails import here but succeeds upstream. Fix: apply the skip refusal and name-mismatch refusal only to ids >= 55, and warn below that. Correct the mod.rs:9-12 doc, add a Deviations row, and add a test for an id below 55.

6. LOW, crates/persistence/src/migrations.rs:269-300 (sql_statements), used by execute_add_column_if_missing at lines 249-257. The splitter does not understand `--` comments. An apostrophe in a leading comment opens a quote that swallows the following ALTER, so later ADD COLUMN statements are silently skipped. A ';' in a comment produces a bad chunk that fails. No shipped SQL triggers this today. Fix: skip `--` and `/* */` while scanning, apply strip_leading_sql_comments per chunk, and add a unit test with an apostrophe and a ';' in a leading comment for a two-ALTER script.

Merged: the two snapshot.rs:157 findings are one item (2). The two snapshot.rs:24/37 leftover and permission findings are split into items 3 and 4.

PASS (no critical or high; one medium, item 1, should be fixed before the import is wired to a caller).

## Confirmed findings (raw)

### [low] Snapshot copy of the live T3 database is created with default (world-readable) permissions
- `crates/persistence/src/t3_import/snapshot.rs:37` · dimension: safety · upheld 2/2
- Evidence: snapshot.rs:37 `tempfile::TempDir::with_prefix_in("turin-t3-import-", SNAPSHOT_DIR)` sets no permissions. tempfile 3.27.0 docs (src/dir/mod.rs:33-35): "Temporary directories are created with the default permissions unless otherwise specified via Builder::permissions. Depending on your platform, this may make them world-readable." The dest file is opened by `Connection::open(dest)` (snapshot.rs:66), which yields 0644 because libsqlite3-sys sqlite3.c:40354 defines SQLITE_DEFAULT_FILE_PERMISSIONS 0644. umask on this machine is 022, so the dir is 0755 and the copy of the whole user T3 database is 0644 in /tmp for the duration of the copy and migration. The same gap exists in adopt.rs:67-70 (`.t3-import-<nanos>` via create_dir, default 0755, inside ~/.turin) and adopt.rs:46 (hard link of a 0644 file into ~/.turin/statev2.sqlite). No set_permissions, from_mode or DirBuilderExt appears anywhere under crates/. Only fresh_schema (verify.rs:142) holds no user data.
- Fix: Create the snapshot dir with tempfile::Builder::new().permissions(std::fs::Permissions::from_mode(0o700)) (and the same for WorkDir via DirBuilder::new().mode(0o700)). Create the copy file with mode 0600 (OpenOptions/OpenOptionsExt or set_permissions before the backup) and apply 0600 to the hard-linked destination, or document the deviation in PORTING.md Deviations.

### [medium] Backup restart loop has no total bound while the live source is being written
- `crates/persistence/src/t3_import/snapshot.rs:80` · dimension: safety · upheld 2/2
- Evidence: snapshot.rs:80 `StepResult::More => pauses = 0,` resets the only counter, and the loop at snapshot.rs:74-100 has no other exit except Done or an error. The sqlite3.h text at line 9661-9663 says: "If the source database is modified by an external process or via a database connection other than the one being used by the backup operation, then the backup will be automatically restarted by the next call to sqlite3_backup_step()." A restarted step returns OK (More), so each external write during the copy resets progress to page 1. T3 Code writes orchestration events continuously during agent turns, so the copy can loop indefinitely on the user's live database. This violates the requirement that busy retries be bounded.
- Fix: Track progress across restarts, for example with backup.progress() (remaining/pagecount). Count restarts, or fail after a fixed wall-clock deadline, and do not reset that counter on More. Return the same busy_err path that the MAX_PAUSES check uses.

### [low] Public T3Import::plan and migrate_and_verify accept any path and open it read-write
- `crates/persistence/src/t3_import/snapshot.rs:157` · dimension: safety · upheld 2/2
- Evidence: snapshot.rs:156-158 `open_snapshot` calls `Connection::open(path)`, which uses rusqlite OpenFlags::default() = READ_WRITE | CREATE (rusqlite-0.40.2/src/lib.rs:1261-1263). It is reached from the public `T3Import::plan(snapshot: impl AsRef<Path>)` (mod.rs:65-68) and `T3Import::migrate_and_verify(snapshot: impl AsRef<Path>)` (mod.rs:72-75), both re-exported from lib.rs:54-56. Nothing checks that the path is a snapshot. Passing ~/.t3/userdata/statev2.sqlite to migrate_and_verify runs BEGIN IMMEDIATE and the pending migrations inside migrations.rs:118-129, writing the live T3 database. plan() opens it read-write and can checkpoint or create it. A missing path is created as an empty file. This breaks the module's own rule (mod.rs:7-8, 80-82 and PORTING.md: never open the T3 file read-write).
- Fix: Open plan() with SQLITE_OPEN_READ_ONLY. Make migrate_and_verify take a T3Snapshot (or make it pub(crate)) so the source path cannot be passed to it. Keep open_snapshot RW only for the internal copy in adopt.rs:37 and verify.rs:144, and refuse a path that is not inside a turin-t3-import- directory.

### [low] Crash or SIGKILL leaves a full copy of the user database in /tmp or ~/.turin
- `crates/persistence/src/t3_import/snapshot.rs:24` · dimension: safety · upheld 2/2
- Evidence: Cleanup relies only on Drop: T3Snapshot's `_dir` (snapshot.rs:25-27) and WorkDir::drop (adopt.rs:74-78). Both are skipped on SIGKILL, power loss or abort. Nothing sweeps stale `turin-t3-import-*` dirs under /tmp or stale `.t3-import-*` dirs under the Turin data dir (adopt.rs:67) at startup. The leftover file is the full, unprotected copy from finding 1.
- Fix: Create the work dirs with restrictive permissions (see finding 1), and remove stale `turin-t3-import-*` and `.t3-import-*` entries before a new import starts, or use a fixed work-dir name that is cleaned on startup.

### [low] Public T3Import::plan and migrate_and_verify open arbitrary paths read-write and migrate them in place
- `crates/persistence/src/t3_import/snapshot.rs:157` · dimension: logic-fidelity · upheld 2/2
- Evidence: snapshot.rs:156-158: `pub(crate) fn open_snapshot(path) { let conn = Connection::open(path)` (read-write, creates if missing). mod.rs:65-68 `pub fn plan(snapshot: impl AsRef<Path>)` and mod.rs:72-75 `pub fn migrate_and_verify(snapshot: impl AsRef<Path>)` both call open_snapshot on the caller's path. migrate_and_verify then calls run_migrations, which writes (verify.rs:64). Nothing checks that the path is a T3Snapshot or a file under /tmp, so passing ~/.t3/userdata/statev2.sqlite would migrate the live T3 database in place, which the task forbids. Current callers (examples/t3_import_check.rs, adopt.rs:37) pass only snapshot copies, so this is latent.
- Fix: Make plan and migrate_and_verify take `&T3Snapshot` (or a private newtype) rather than `impl AsRef<Path>`, so only copies made by T3Import::snapshot can reach the writable open. If a path-based API must stay, open plan read-only with SQLITE_OPEN_READ_ONLY and refuse to migrate any path that is not a snapshot.

### [low] Add-column guard splitter is not comment-aware, so a ';' or quote inside a -- comment can skip a column add
- `crates/persistence/src/migrations.rs:269` · dimension: logic-fidelity · upheld 2/2
- Evidence: sql_statements (migrations.rs:269-300) tracks quotes and splits on ';' without knowing about `--` comments. Throwaway harness (copied functions, rustc, not run against any DB): input "-- don't touch the next column\nALTER TABLE t ADD COLUMN a TEXT;\nALTER TABLE t ADD COLUMN b TEXT;" yields ONE statement with add_column_target == Some(("t","a")). If column `a` already exists (partially migrated DB), execute_add_column_if_missing (migrations.rs:249-257, `continue`) skips the whole chunk, so `b` is never added and the ledger row is still recorded. Input "-- note; see below\nALTER TABLE t ADD COLUMN c TEXT;" yields "see below\nALTER..." which fails add_column_target, so the guard is bypassed and a duplicate-column error results. No current SQL file under crates/persistence/sql has a quote or ';' in a comment (only 027 has leading comments, and those are clean), so this is latent.
- Fix: Make sql_statements skip `--` line comments (and `/* */` blocks) while scanning, before the quote and ';' handling, and apply strip_leading_sql_comments to each chunk. Add a unit test with an apostrophe and a ';' inside a leading comment for a two-ALTER script.
