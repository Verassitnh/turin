## Lead report

1. [medium] crates/providers/src/provider_registry.rs:906-916 (stale comment at :840-842). The per-instance change task owns the managed Arc through `ProviderSnapshotSource`, so the stream never ends and replaced or removed instances leak their managed provider. The retired provider keeps publishing through `sync_provider`, which upserts by instance_id with no liveness check. A stale snapshot can overwrite a rebuilt instance or re-add a removed ghost. Upstream ends the subscription when the instance scope closes (ProviderRegistry.ts:822-826, 888-892; managedProvider.ts:60-63). Fix: cancel the task when the instance scope closes (token fired by `ProviderInstanceScope::close`, `select!` in the loop). Drop the Arc before spawning and keep only the receiver plus captured instance_id and driver_kind. Guard `sync_provider` with a liveness or ptr_eq check against live subscriptions. Add a test that rebuilds or removes an instance and asserts the old subscription stops forwarding and the old provider drops. The "stale health-interval probes" part of the original claim does not apply to production drivers, since Claude and Cursor have no timers. The first pass rated this high; verification downgraded it to medium.

2. [low] crates/provider-core/src/managed_provider.rs:362-367 (interval loop ~404-411 has the same pattern). The settings loop logs and continues after an `apply_snapshot` failure. Upstream managedProvider.ts:265-267 is a forkScoped `runForEach` with no catch, so the fiber ends on the first failure. Divergence is not in PORTING.md Deviations. Fix: add a Deviations row covering both loops, or break out on error to match upstream.

3. [low] crates/provider-core/src/provider_compatibility.rs:58-66. `is_version_range` accepts empty or whitespace-only `||` groups ("1.0.0||", "||", ">=1 || "). `split_whitespace` yields no tokens, so `all()` is vacuously true. Upstream providerCompatibility.ts:17-24 trims each group and splits on /\s+/, so an empty group fails the token regex. Fix: trim each group, split on whitespace keeping empty tokens, and require every token to match. Add these cases to `rejects_invalid_ranges_and_recommendations_outside_the_first_supported_match` (test near :607).

4. [low] crates/provider-core/src/model_catalog.rs:149-159. `apply_catalog_default` sets `aliases` to None when the merged list is empty, dropping a model's own `aliases: []`. Upstream ModelCatalog.ts:145-146 keeps it via the spread. Only the wire key presence differs, and only remote manifests with `"aliases": []` reach it. Fix: `if !aliases.is_empty() { model.aliases = Some(aliases); }`.

5. [low] crates/provider-core/src/provider_host_live.rs:100-104. `with_settings_snapshot` holds the RwLock read guard across `job(...).await`. tokio's RwLock is write-preferring, so a job that calls `get_settings` while `update_settings` is queued deadlocks (reproduced with a standalone tokio 1.53.3 program). Upstream serverSettings.ts runs jobs under writeSemaphore and serves reads from cache. Latent, since there is no non-test caller on this branch. Fix: clone the settings under a short read lock and run the job on the clone, or serialize writes with a separate Mutex. Also correct the comment at :102-103, which claims parity with upstream.

6. [low] crates/providers/src/provider_maintenance_runner.rs:516-523, 552-564. The progress sampler is aborted through `AbortOnDrop` but not awaited. A sampler poll already in flight can write a stale Running state (via `set_provider_maintenance_action_state`, provider_registry.rs:691-702) after the caller writes Failed or Verifying. The stale state persists until the next update. The window is very small. Upstream providerMaintenanceRunner.ts:123-130 under `Effect.scoped` waits for interruption. Fix: keep the JoinHandle, then `abort()` and `await` it before returning, or gate the sink behind a closed flag under the same lock.

7. [low] crates/provider-core/src/provider_status_cache.rs:216-224. The test `an_invalid_cache_file_reads_as_none_without_retaining_its_contents` asserts only `is_none()`. Upstream providerStatusCache.test.ts:46-76 also checks logged path, string errorTag, absence of cause and issues, and absence of the secret. The code logs only path and error_kind (:146-150), so behaviour looks right, but the no-retention property is untested. Fix: capture tracing output in the test and assert those fields, or note in the test header that log assertions were not ported.

### [high] Replaced or removed instance's managed provider is never torn down, so stale probes keep overwriting registry state
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/R1-provider-registry/crates/providers/src/provider_registry.rs:906` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust (provider_registry.rs:906-916): `let source = build_snapshot_source(instance); let mut changes = source.stream_changes(); ... self.tasks.spawn(async move { while let Some(provider) = changes.next().await { let provider = correlate_snapshot_with_source(&source, provider); inner.sync_provider(...).await; } });`. `source` is a `ProviderSnapshotSource` holding `Arc<dyn ManagedServerProvider>` (build_snapshot_source at :343 clones `instance.snapshot`). The spawned task owns `source` until the stream ends, and the stream only ends when the managed provider drops. But `ManagedServerProvider::drop` (the only thing that aborts its interval/settings/initial tasks, managed_provider.rs Drop impl) never runs while the task holds the Arc. Upstream instead forks `Stream.runForEach(source.streamChanges, ...)` into the layer scope (ProviderRegistry.ts:888-892) and relies on the old child scope closing to end it (ProviderRegistry.ts:823-825 doc: 'its PubSub shuts down and our Stream.runForEach fiber exits naturally'); the managed provider's loops are forkScoped (managedProvider.ts:261, 267, 296, 300). Rust's own comment at provider_registry.rs:840-842 ('When a rebuilt instance's old scope closes, its stream ends') is therefore false. Consequences: after a settings change rebuilds instance X (the rebuilt branch of sync_live_sources), the old managed provider keeps running its health-interval probes against the old executable and publishes through this task; sync_provider upserts by instance_id, so the stale snapshot overwrites X'. After an instance is removed, its stale stream can re-add a ghost entry that upstream's pruning step (ProviderRegistry.ts:923-925, 'otherwise the UI would keep rendering ghosts') removes. No registry test asserts teardown (grep for strong_count/Weak/stale in provider_registry/tests.rs finds nothing). Upstream ProviderRegistry.ts:888-892 is the reference.
- Fix: Do not let the subscription task own the managed Arc. Capture only instance_id and driver_kind (clones) plus the receiver, e.g. `let (instance_id, driver_kind) = (instance.instance_id.clone(), instance.driver_kind.clone()); let mut changes = build_snapshot_source(instance).stream_changes();` with the source dropped before spawning, and correlate against the captured ids. Add a test: rebuild or remove an instance, drop the registry's references, and assert the old managed provider's Drop ran (Weak::upgrade is None) and that a late emission from the old instance does not reach get_providers.

### [medium] Per-instance change subscription keeps the retired managed provider alive, so rebuilt/removed instances never stop and their stale snapshots overwrite live state
- `crates/providers/src/provider_registry.rs:` · dimension: robustness · upheld 2/2
- Evidence: provider_registry.rs:907-916: `let source = build_snapshot_source(instance); let mut changes = source.stream_changes(); self.tasks.spawn(async move { while let Some(provider) = changes.next().await { let provider = correlate_snapshot_with_source(&source, provider); inner.sync_provider(provider, ..).await; } });` The async block owns `source`, a ProviderSnapshotSource holding `managed: Arc<dyn ManagedServerProvider>` (built_in_provider_catalog.rs:24). The stream is a WatchStream over `changes: watch::Sender` stored inside that same object (claude_managed_provider.rs:294, stream_changes at 372-374). The stream therefore cannot end while the task holds the object, and the object cannot drop while the stream is open. Instance close does not break the cycle: claude_driver.rs:280-287 only aborts the warm probe in on_close. The comment at provider_registry.rs:840-842 says 'its stream ends and our loop exits naturally', which is false here. Upstream relies on the managed PubSub being shut down with the instance scope (managedProvider.ts:63 acquireRelease(PubSub.unbounded, PubSub.shutdown); stream at :309; ProviderRegistry.ts:824-826 'its PubSub shuts down ... our fiber exits'). Effects: each settings rebuild or removal leaks one permanent task and keeps the old managed provider (and its probes/adapters) alive. Any later emission from the retired instance goes through sync_provider (provider_registry.rs:913-914 -> upsert_providers merges by instance_id, :594-596), so it overwrites the rebuilt instance's snapshot or re-adds a removed instance to the aggregate list. Not executed; traced statically.
- Fix: End the per-instance subscription when that instance's scope closes: give ProviderInstance a cancellation token that ProviderInstanceScope::close fires, and select! on it in the loop at provider_registry.rs:909-915 so the task exits and drops `source`. Also avoid holding the managed Arc in the task beyond the stream (e.g. only move the stream, or check Arc::ptr_eq against live_subs before sync_provider). Add a registry test that removes/rebuilds an instance and asserts the old subscription stops forwarding.

### [low] Settings read lock is held across the whole job in with_settings_snapshot, so a queued settings write deadlocks any re-entrant read
- `crates/provider-core/src/provider_host_live.rs:` · dimension: robustness · upheld 2/2
- Evidence: provider_host_live.rs:101-104: `let snapshot = settings.current.read().await; Ok(job(snapshot.clone()).await)` keeps the RwLock read guard alive across `job(...).await`. update_settings takes `*self.settings.current.write().await` (line 51). tokio's RwLock is fair/write-preferring (tokio-1.53.3 src/sync/rwlock.rs:41-43), so once a writer is queued every new reader blocks, including get_settings (managed_provider.rs:298, snapshot_settings.rs:51, provider_host_live.rs:146). If the job calls host.get_settings() while update_settings is queued, the job waits on the new reader, the writer waits on the job's guard, and the pair deadlocks. Also, every get_settings stalls for the whole job. Upstream serverSettings.ts:281-282 runs the job under writeSemaphore (not a read lock over the value) and reads come from cache, so reads never wait behind a job. No non-test caller of with_settings_snapshot exists in this branch (grep), so this is latent for the driver crates that will call it.
- Fix: Do not hold the RwLock guard during the job. Clone the settings out under a short read lock and run the job on the clone, or serialize mutations with a separate tokio Mutex like upstream's writeSemaphore so reads are never blocked by a job.

### [low] Progress sampler is aborted but not awaited, so a late progress write can overwrite the final update state
- `crates/providers/src/provider_maintenance_runner.rs:` · dimension: robustness · upheld 2/2
- Evidence: provider_maintenance_runner.rs:516-523: `struct AbortOnDrop(JoinHandle<()>); impl Drop { fn drop(&mut self) { self.0.abort(); } }` and 552-564 spawn the sampler with `let _sampler = AbortOnDrop(tokio::spawn(...))`, which runs `on_progress(line).await` in a loop. tokio abort() is asynchronous. The sampler can be mid-poll on another worker when `collect` finishes, so its set_provider_maintenance_action_state (lines 965-987, which inserts the Running state synchronously) can land after run_command_and_verify has already written Failed (lines 1000-1011) or the Verifying Running state (1014-1018). The stale Running state then stays in maintenance_update_states until the next update. The window is narrow. Upstream providerMaintenanceRunner.ts:123-130 forks the sampler with forkScoped under Effect.scoped (line 188), and scope close waits for interruption, so no progress write can follow the result.
- Fix: Keep the JoinHandle and await it after abort() before returning from run_provider_maintenance_command (or gate the progress sink behind a closed flag checked under the same lock as the state write). Either way, no sampler write may happen after the caller writes the final state.
