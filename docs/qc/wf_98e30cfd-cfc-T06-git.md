## Confirmed findings (raw)

### [high] Commit ignores upstream 10-minute timeout, so slow pre-commit hooks get killed at 30s
- `crates/git/src/git_manager.rs:1036` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust commit_step passes `GitCommitOptions { stage: ..., ..GitCommitOptions::default() }` (git_manager.rs:1036-1038), so `timeout` is None. In driver_body.rs:853-855 `call.timeout` is only set when `options.timeout` is Some, so the default 30s applies (git_vcs_driver_core.rs execute: `input.timeout.unwrap_or(Some(DEFAULT_TIMEOUT))`). Upstream GitManager.ts:2194 passes `timeoutMs: COMMIT_TIMEOUT_MS` (10 * 60_000, line 169) into gitCore.commit, and GitVcsDriverCore.ts commit forwards it to executeGit. On timeout process.rs:482 calls kill_tree, so a pre-commit hook (lint, test) running longer than 30s aborts the commit in Turin but completes upstream.
- Fix: In commit_step set `timeout: Some(Duration::from_secs(600))` on GitCommitOptions (define COMMIT_TIMEOUT as a const matching upstream COMMIT_TIMEOUT_MS).

### [medium] Custom commit message is rewritten (trailing dots stripped, cut to 72 chars) before committing
- `crates/git/src/git_manager.rs:1056` · dimension: logic-fidelity · upheld 2/2
- Evidence: git_manager.rs:1056-1057: `if let Some(message) = commit_message.and_then(parse_custom_commit_message) { return Ok(sanitize_commit_message(message.0, message.1, None)); }`. sanitize_commit_message (line ~1484) does `trim_end_matches('.')` and `.chars().take(72)`. Upstream GitManager.ts:2065-2071 returns the custom subject and body unchanged (`subject: customCommit.subject, body: customCommit.body`) with no sanitizeCommitMessage call; sanitizeCommitMessage (line 562-572) is applied only to generated text at line 2089. So 'Fix bug.' is committed as 'Fix bug' in Turin, and feature-branch names derived from a >72-char custom subject are truncated. Note also JS slice(0,72) counts UTF-16 units while Rust chars().take(72) counts scalar values, which diverges for astral characters.
- Fix: Return the parsed custom subject/body directly on the custom path (skip sanitize_commit_message), matching upstream lines 2065-2071; apply sanitize only to generated text.

### [low] Sorting uses byte order where upstream uses JS localeCompare
- `crates/git/src/checkpointing/diffs.rs:40` · dimension: logic-fidelity · upheld 2/2
- Evidence: diffs.rs:40 `files.sort_by(|left, right| left.path.cmp(&right.path))`. Upstream Diffs.ts:36 uses `left.path.localeCompare(right.path)`. Same mismatch: driver_body.rs:747 (upstream GitVcsDriverCore.ts:2095/2101 localeCompare), driver_rest.rs:788 branch tie-break (upstream 3282 `left.ref.name.localeCompare(right.ref.name)`), workspace_entries.rs:221 (upstream WorkspaceEntries.ts:233), workspace_search_index.rs:372 (upstream WorkspaceSearchIndex.ts:456-457). Verified with node: sorting ["B.ts","a.ts","_x","Zed","e.ts","émile"] with localeCompare gives _x, a.ts, B.ts, e.ts, émile, Zed; byte order gives B.ts, Zed, _x, a.ts, e.ts, émile. Visible list order changes, and the 25k cap in WorkspaceSearchIndex keeps a different subset.
- Fix: Use an ICU root-locale collator (e.g. icu_collator with the root locale) for these comparisons, matching localeCompare, or document the deviation in PORTING.md Deviations.

### [low] Restore's clean-failure check is looser than upstream's regex
- `crates/git/src/git_vcs_driver.rs:490` · dimension: logic-fidelity · upheld 2/2
- Evidence: Rust: `.stderr.trim().starts_with("warning: failed to remove ./:")`. Upstream GitVcsDriver.ts:1133-1136 requires `/^warning: failed to remove \.\/: [^\n]+$/.test(cleaned.stderr.trim())`. Rust therefore accepts a bare 'warning: failed to remove ./:' with no detail, or a multi-line stderr that upstream rejects, and proceeds when the workspace is empty. The emptied check still applies, so data loss is unlikely, but the behaviour differs.
- Fix: Match the upstream pattern: a single line, `^warning: failed to remove \./: .+$`, applied to the trimmed stderr.

### [medium] SIGKILL on timeout, abort, or drop leaves stale .git lock files in the user's repository
- `crates/git/src/process.rs:` · dimension: safety-and-concurrency · upheld 2/2
- Evidence: process.rs:495-503 kill_group sends libc::kill(-(pid), libc::SIGKILL). Callers: KillGroupGuard drop (line 226, 487-491), kill_tree on timeout (line 279) and on joined Err (line 308). Upstream sends SIGTERM to the process group (upstream/apps/server/node_modules/@effect/platform-node-shared/src/NodeChildProcessSpawner.ts:503, signalGroup(options?.killSignal ?? "SIGTERM"), with escalation only when forceKillAfter is set). Git's common signal handlers remove .git/index.lock and ref lock files on SIGINT/SIGHUP/SIGTERM; SIGKILL bypasses that. The status poller can abort a mid-flight `git pull --ff-only` (vcs_status_broadcaster.rs:420 AbortOnDropHandle around remote_refresh_loop, which reaches pull_current_branch at vcs_status_broadcaster.rs:611). A 60s timeout on `git add -A` or `git commit` has the same effect. The next git command in that checkout then fails with 'Unable to create .git/index.lock: File exists' until someone deletes the file by hand. Upstream's own comment at GitVcsDriver.ts:836 notes that forced termination can leave the index lock behind.
- Fix: Send SIGTERM to the group first (kill(-pid, SIGTERM)), wait a short grace period, then SIGKILL. Apply the same change to KillGroupGuard. Alternatively, follow upstream and use SIGTERM only, with no forced kill by default. Record the change in the Deviations table if it stays.

### [low] Checkpoint temp index is not removed when capture_checkpoint is cancelled
- `crates/git/src/git_vcs_driver.rs:` · dimension: safety-and-concurrency · upheld 2/2
- Evidence: git_vcs_driver.rs:411-417: capture_checkpoint creates `t3-checkpoint-index-{uuid}` in the git common dir, awaits capture_with_index, then calls remove_force on the index and its .lock. The cleanup is straight-line code after the await, not a drop guard. If the returned future is dropped mid-capture (caller abort, timeout, select), the temp index and its .lock stay in .git/. Upstream registers cleanupTempIndex as an Effect finalizer that runs on interruption (upstream/apps/server/src/vcs/GitVcsDriver.ts:836-841). Combined with the SIGKILL finding above, the .lock is the case upstream explicitly guards against.
- Fix: Put the two paths in a small RAII guard whose Drop calls std::fs::remove_file on temp_index and temp_index.lock. Keep the explicit cleanup for the normal path, or let the guard handle both.

### [medium] PR lookup failure backoff never escalates because the failure streak is hardcoded to 1
- `crates/git/src/git_manager.rs:` · dimension: safety-and-concurrency · upheld 2/2
- Evidence: git_manager.rs:647 `let failures = 1;` then `pr_lookup_failure_ttl(failures)` on the Err arm (line ~650). Every failed branch PR lookup is cached for PR_LOOKUP_FAILURE_BASE (20s) and the exponential backoff in pr_lookup_failure_ttl is never reached. Upstream keeps a per-key streak (upstream/apps/server/src/git/GitManager.ts:1161-1176, nextPrLookupFailureTtl), increments it on each failure, deletes it on success (line 1238), and bounds it with PR_LOOKUP_CACHE_CAPACITY. With GitHub rate-limited or unreachable, Turin re-invokes `gh` every 20s per branch indefinitely. Upstream's comment at GitManager.ts:179 describes exactly this throttling pressure.
- Fix: Add a Mutex<Lru> or HashMap<String, u32> streak keyed by the pr cache key. Increment it on Err, remove it on Ok, and pass the new count to pr_lookup_failure_ttl. Bound it at PR_LOOKUP_CACHE_CAPACITY like upstream.

### [low] Streaming line callback decodes UTF-8 per 8 KiB chunk, corrupting multibyte characters split across reads
- `crates/git/src/git_vcs_driver_core.rs:` · dimension: safety-and-concurrency · upheld 2/2
- Evidence: git_vcs_driver_core.rs:857: `pending.push_str(&String::from_utf8_lossy(chunk));`. process.rs:collect_stream reads pipes into an 8192-byte buffer and passes each raw chunk to the callback. A multibyte UTF-8 sequence that straddles a read boundary is decoded as U+FFFD on both sides, so the streamed commit/push/submodule output lines show replacement characters. The final collected stdout is decoded once and is not affected.
- Fix: Keep a trailing incomplete byte sequence in the LineTail buffer as bytes, and decode only up to the last complete UTF-8 boundary before appending. Or buffer raw bytes and split lines on b'\n' / b'\r' before decoding.

### [low] Undocumented process-group deviation: detaches git from the controlling terminal and SIGKILLs leftovers after success
- `crates/git/src/process.rs:` · dimension: safety-and-concurrency · upheld 1/2
- Evidence: process.rs:213 `command.process_group(0);` puts every git child in its own process group, so a git credential or ssh prompt that reads /dev/tty from a background group gets SIGTTIN and stops. Upstream children stay in the foreground group (NodeChildProcessSpawner.ts, no process-group change for these calls). process.rs:322 `kill_group(pid);` runs after every successful exit and SIGKILLs any descendant still in the group, such as a post-commit hook that starts a background process with &. Upstream does not kill those on normal exit. Neither change is in the PORTING.md Deviations table, which ground rule 4 requires.
- Fix: Add a Deviations row describing both effects, or drop the post-exit kill_group call and the process_group(0) if the terminal-prompt regression matters for Turin's launch modes (terminal-launched vs Finder-launched).
