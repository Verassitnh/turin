## Confirmed findings (raw)

### [low] format_usd rounds with toFixed semantics where Intl currency rounds the shortest decimal (half-expand)
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/T05c-shared-usage-tools/crates/shared/src/usage_format.rs:28` · dimension: logic-fidelity · upheld 2/2
- Evidence: Node: new Intl.NumberFormat('en-US',{style:'currency',currency:'USD',min/maxFractionDigits:2}).format(v) gives 1.005 -> "$1.01", 0.615 -> "$0.62", 2.675 -> "$2.68", 1234.565 -> "$1,234.57"; (v).toFixed(2) gives 1.00 / 0.61 / 2.67 / 1234.57. Rust format_usd calls js_to_fixed(value.abs(), 2) (line 28). js_to_fixed only special-cases exact binary ties (1.005*8 is not an integer), so it falls through to format!("{:.2}") on the exact binary value and returns "$1.00", "$0.61", "$2.67". Upstream usageFormat.ts:11-22 uses Intl.NumberFormat, so the shown cost differs by one cent on values whose shortest decimal ends in 5 at the third place.
- Fix: Round the shortest round-trip decimal (Rust format!("{}", abs), which is shortest-repr) to 2 fraction digits, rounding half away from zero on that decimal string, then group thousands. Keep js_to_fixed for toFixed call sites (format_percent, trim) where toFixed is the upstream function. Add asserts for format_usd(1.005)="$1.01" and format_usd(0.615)="$0.62".

### [low] JS '.' and '(?m)^' exclude or split on CR/LS/PS, fancy-regex and regex do not
- `/Users/jackson/.t3/scratch/2026-10-15-consider-creating-a-t3-code-21b503f2/turin-wt/T05c-shared-usage-tools/crates/shared/src/composer_context_legacy.rs:104` · dimension: logic-fidelity · upheld 2/2

Upstream composerContextLegacy.ts:135 applies that regex per line, so a CRLF element-context line drops the field. Rust ELEMENT_FIELD (line 103-104) is Regex::new(r"^([a-z]+): (.*)$"), where '.' matches \r, so pageUrl/selector keep a trailing \r. Also JS (?m)^ matches after \r,   and  , but the Rust (?m) patterns at lines 68 (REVIEW_OR_CONTEXT_BLOCK) and 75 (REVIEW_BOUNDARY) only match after \n, so a review fence after a lone CR is found by JS and missed by Rust.
- Fix: Define JS_DOT = "[^\\n\\r\\u{2028}\\u{2029}]" in js_string.rs and use it for every upstream '.' (ELEMENT_FIELD, SOURCE_LOCATION). For the (?m) anchors, replace '^' with (?:^|(?<=[\\r\\u{2028}\\u{2029}])) (fancy-regex supports lookbehind). Add tests with a CRLF element block and a lone-CR review fence, checked against node output.

### [low] Review-token Regex::new().expect panics on a run of 32768 U+E000 characters
- `crates/shared/src/composer_context_legacy.rs:593` · dimension: safety-and-rules · upheld 2/2
- Evidence: Lines 592-596: `while text.contains(&review_token) { review_token = format!("{review_token}{review_token}"); }` then `Regex::new(&format!("{token}([0-9]+){token}")).expect("token regex")` and the same for `trailing_review_tokens`. The token doubles until it is longer than the longest U+E000 run in the message. A run of 32768 chars gives a 65536-char token. Probe with the regex crate (release, same expression): run=20000 gives token 32768 and compiles; run=40000 gives token 65536 and fails with 'Compiled regex exceeds size limit of 10485760 bytes', so `.expect` panics. The trigger is any message containing a legacy marker such as '<element_context>' plus that run. upgrade_legacy_context_message runs on read (module doc), so a persisted message would panic every time the thread loads. The regexes are also compiled per call, not cached.
- Fix: Do not panic on the token regex. Either return `unchanged()` when `Regex::new` fails, or drop the regex for the token scan and match the placeholder with a char scan. Also choose a placeholder that does not grow with input (or escape-check the text once) so the pattern size stays bounded.

### [low] Line-count arithmetic overflows on untrusted u64 line range (debug panic, release miscount)
- `crates/shared/src/composer_context_legacy_send.rs:158` · dimension: safety-and-rules · upheld 2/2
- Evidence: `let count = (record.line_end as i64 - record.line_start as i64 + 1).max(0) as usize;` (same expression at crates/shared/src/composer_context_references.rs:362). lineStart/lineEnd are `NonNegativeInt = u64` with no upper bound (crates/contracts/src/base_schemas.rs:191; upstream composerContext.ts uses NonNegativeInt, which is a safe-integer Int). Clipboard fragments are untrusted (composer_context_clipboard.rs comments say so) and only require lineEnd >= lineStart. Probe: lineStart=0, lineEnd=i64::MAX gives 'attempt to add with overflow' under overflow-checks (dev profile); lineStart=0, lineEnd=2^63 gives count=0 in release, so the whole terminal body is dropped.
- Fix: Use checked or saturating arithmetic on u64 (`line_end.saturating_sub(line_start).saturating_add(1)`), and/or bound line numbers to the JS safe-integer range in the contract deserializer as upstream does.

### [low] href_link rescans to the next ']' or newline for every '[' (quadratic)
- `crates/shared/src/thread_links.rs:187` · dimension: safety-and-rules · upheld 2/2
- Evidence: `fn href_link` runs `(start + 1..chars.len()).find(|&at| chars[at] == ']' || chars[at] == '\n')?` for each '[' start that scan_outside_code visits. Nothing caches the delimiter position, unlike markdown_links.rs `markdown_run_end_finder`. Timing probe of the same loop on '['.repeat(n): n=20000 took 58ms, n=40000 took 270ms (about 4.7x for 2x input). Input comes from message markdown (assistant output is partly untrusted), and relabel_thread_links runs over it.
- Fix: Cache the next ']'/'\n' position as markdown_links::markdown_run_end_finder does (monotonic cursor), so one pass over the chars covers all '[' starts.

### [low] Quadratic allocation in change_request_repository_url path scan
- `crates/shared/src/change_request_url.rs:345` · dimension: safety-and-rules · upheld 2/2
- Evidence: `(0..path.len()).filter(|&index| path.is_char_boundary(index)).find_map(|index| { let rest = path[index..].to_ascii_lowercase(); ... })` copies the whole remainder of the path at every index until the first '/pull' match. parse_change_request_url only checks the path shape `^/([^/]+/[^/]+)/pull/([0-9]+)`, so owner and repo segments have no length bound. A long owner/repo segment costs about len^2/2 bytes of allocation.
- Fix: Compare the prefix in place without allocating, e.g. `path.as_bytes()[index..].get(..5).is_some_and(|b| b.eq_ignore_ascii_case(b"/pull"))`, then parse the digits from the bytes.

### [low] locale_compare u32 overflow on five combining marks (main, outside branch diff)
- `crates/shared/src/js_string.rs:165` · dimension: safety-and-rules · upheld 2/2
- Evidence: `*last = *last * 1000 + (c as u32 - 0x2ff);` inside locale_compare's key(). Each U+0300..U+036F mark on a base character multiplies the accumulator by 1000. Probe with the same arithmetic and overflow-checks=on: 'a' followed by five U+0301 gives 2, 2002, 2002002, 2002002002, then 'attempt to multiply with overflow'. Release builds wrap and silently reorder. This function is on main (T05a), not in the branch diff, so this is noted for follow-up rather than as a branch defect.
- Fix: Use u64 or saturating_mul/saturating_add for the secondary key, or compare accent sequences lexicographically instead of folding them into one integer.
