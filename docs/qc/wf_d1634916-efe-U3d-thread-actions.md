Confirmed: 4 · refuted: 1

## Lead report

1. MEDIUM: use_handle_new_thread.rs:190-195 (NewDraftFields) and :109-145 (ReusedDraftWorkspace / reused_draft_workspace) drop the target environment's runtimeMode. Upstream useHandleNewThread.ts:150 reads projectSettings.settings.defaultRuntimeMode and writes it at :285 and :322 (reused empty draft, only when !isDraftAlreadyOpen) and :435 (mint-fresh draft). The Rust port has no runtime mode anywhere in this path, and PORTING.md logs no omission. Fix: add runtime_mode to NewDraftFields and to the reused-draft decision, fed from projectSettings.defaultRuntimeMode, gated on !isDraftAlreadyOpen, including when explicit options are passed. Add tests mirroring useHandleNewThread.test.ts:212-232. Alternatively, log the omission with a reason in the PORTING.md Deviations row.

2. MEDIUM: docs/handoff/U3d.md:58-59 excuses the skipped showThreadUndoNotice cases as "browser and terminal cases". Neither showThreadUndoNotice.test.ts nor useThreadActions.test.ts has any such case. The three skipped cases are kept behaviour, not cut-list items: "reports a failed restore and releases its claim" (:94), "reports a rejected restore promise" (:107), and "does not report interrupted restores as errors" (:121). No Rust test covers undo failure toasts. The handoff also says run_undo_plan "raises the same toast", which is false for interrupts (see item 3). Fix: correct the handoff and PORTING.md rationale, and port the three cases as tests. Do not log them as cut-list skips.

3. LOW: use_thread_actions.rs:389-395 (undo_notice) shows an error toast for every Err from run_undo_plan. An interrupted restore becomes ThreadActionError::Dispatch(CommandFailure::Interrupted) and shows "The command was interrupted." Upstream showThreadUndoNotice.ts:75 suppresses the toast when `!isAtomCommandInterrupted(result)`. The trigger is latent: the only ThreadCommands impl in the crate is the test FakeCommands. Fix: skip the toast when is_command_interrupted(), keep the failed-restore and dispatch-error toasts, and add a test where an interrupted dispatch produces no toast. This is covered by the test port in item 2.

4. LOW: thread_undo.rs:243-250 (take_undo) returns taken offers in insertion order, oldest first, because state.live.retain visits front to back. undo_notice (use_thread_actions.rs:389-395) runs them in that order. Upstream showThreadUndoNotice.ts:43-47 builds the group newest first, and :63 calls current.map(async ...) in that order, so undo() starts newest first. PORTING.md:439-441 claims the ordering is ported, so this is an unlogged divergence. Fix: order the taken offers to match the notice's ids (newest first), or reverse them in take_undo. Add a test with two same-kind offers that asserts dispatch order. The existing tests (thread_undo_tests.rs:82-105, showThreadUndoNotice.test.ts:35-54) do not catch it.

Verdict: PASS (no critical/high; highest is medium). Fixes 1-4 are still required before merge.
