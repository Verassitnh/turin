## Lead report

1. low | crates/codex-app-server/src/client.rs:211 (Drop 336-339, shutdown 281-285 and 293-297): the process group is never signalled once the leader exits, because child_pid is zeroed at line 211. Descendants survive drop or shutdown, which contradicts PORTING.md:95. Fix: store the pgid separately from the liveness flag and always signal -pgid on shutdown and drop. Guard against pid reuse once the group empties, either by SIGKILLing the group from the wait task right after reaping or by documenting the limitation. Add an orphan-after-exit test. One verifier rated this medium.
2. low | client.rs:83 and 110-113: a known server-request method with no registered handler falls through to the unknown-request handler. Upstream answers -32601 for these. Fix: check the known-method table first. A known method with no handler returns Err(ProtocolError::method_not_found). Only unknown methods reach `unknown`. Add a test with an unknown handler registered.
3. low | client.rs:122-139: a known notification with no registered handler reaches the unknown-notification handler. Handlers registered under names outside SERVER_NOTIFICATION_METHODS are also invoked. Fix: check membership in SERVER_NOTIFICATION_METHODS. Known methods go only to their registered handlers, with no-op when there are none. Unknown methods go to the unknown handler. Reject or ignore registrations for non-protocol names.
4. low | client.rs:135-137: the loop `let _ = handler(...)` keeps running after a handler returns Err. Upstream Effect.forEach short-circuits. Fix: break on the first Err, or log the all-handlers behaviour in the PORTING.md Deviations table.
5. low | client.rs:96-101: non-Request handler errors send `data: Some(Value::String(..))` on the wire. Upstream sends no data. Fix: set data to None, or add a Deviations row.
6. low | client.rs:326-331 (used at 92 and 108): the message is "Invalid params: {detail}". Upstream is "Invalid payload for method '<m>' during 'decode-payload'|'encode-payload'", and the tests assert that text. The unexpected and missing payload messages in schema.rs:90-96 also differ from upstream's "Method '<m>' does not accept a payload during '<op>'". Fix: use the upstream message formats, with method and phase taken from the call sites. Log the data-object difference in Deviations.
7. low | protocol.rs:226 and 311-317: BufReader::lines() rejects invalid UTF-8, and the read loop then fails the whole session. Upstream Stream.decodeText substitutes U+FFFD. Fix: read per line with read_until(b'\n'), decode with String::from_utf8_lossy, and trim a trailing \r. Or add a Deviations row.
8. low | crates/codex-app-server/src/tests.rs (coverage): no tests for the upstream schema.test.ts codexErrorInfo cases (rateLimitExceeded, misalignmentPolicyViolation), the rateLimits response with rateLimitResetCredits, or the consume reset response (protocol.test.ts:55-130). Also no test for the handler-error mapping (shared.test.ts). Fix: port the schema cases through schema::validate_type and add tests for items 2, 4, 5 and the handler-error mapping. Termination-interrupts-handler is a transport test that PORTING.md rule 5 exempts, so it is optional.

## Confirmed findings (raw)

### [low] Known server-request methods with no registered handler are routed to the unknown-request handler instead of method-not-found
- `crates/codex-app-server/src/client.rs:` · dimension: protocol-fidelity · upheld 2/2
- Evidence: client.rs:85 `let handler = requests.requests.lock().get(&method).cloned();` then client.rs:110-113 `} else if let Some(handler) = unknown { handler(method, params).await } else { Err(ProtocolError::method_not_found(&method)) }`. Upstream client.ts dispatchRequest only consults unknownRequestHandler when `request.method in CodexRpc.SERVER_REQUEST_PARAMS` is false; for a known method, runHandler (_internal/shared.ts) returns `CodexRequestError.methodNotFound(method)` when no handler is set. So in Rust a known method with no handler is answered by the unknown handler (which may return success), while upstream always answers -32601.
- Fix: In dispatch, branch on whether the method is a known server-request method first. Known method + no handler => Err(ProtocolError::method_not_found(&method)). Only unknown methods fall through to `unknown`. Add a test that registers an unknown-request handler and sends a known server-request method with no handler, expecting -32601.

### [low] Known notifications with no registered handler are passed to the unknown-notification handler
- `crates/codex-app-server/src/client.rs:` · dimension: protocol-fidelity · upheld 2/2
- Evidence: client.rs:124 `if let Some(handlers) = handlers { ... } else if let Some(handler) = unknown { handler(method, params).await }` (client.rs:138-139). Upstream client.ts dispatchNotification: `if (schema) { decode ... }` and only `return unknownNotificationHandler ? ... : Effect.void` when there is no schema. A known method never reaches the unknown handler upstream. Rust also dispatches to handlers registered under method names that are not in SERVER_NOTIFICATION_METHODS (client.rs:124-137 does no known-method check), which upstream never does.
- Fix: Mirror dispatchNotification: if the method is in SERVER_NOTIFICATION_METHODS, decode/validate and call only its registered handlers (no-op when none); otherwise call the unknown handler. Ignore handlers registered for unknown method names, or reject them at registration.

### [low] Remaining notification handlers run after an earlier handler fails
- `crates/codex-app-server/src/client.rs:` · dimension: protocol-fidelity · upheld 2/2
- Evidence: client.rs:135-137 `for handler in handlers { let _ = handler(params.clone()).await; }`. Upstream client.ts dispatchNotification uses `Effect.forEach(handlers, (handler) => handler(decoded), { discard: true })` piped to `Effect.ignore`. Effect.forEach is sequential and short-circuits on the first failure, so later handlers are skipped upstream but all run in Rust.
- Fix: Stop the loop on the first Err (`for handler in handlers { if handler(params.clone()).await.is_err() { break; } }`), and record the divergence in Deviations if all-handlers delivery is intended.

### [low] Handler failures put the internal error text into the wire error data
- `crates/codex-app-server/src/client.rs:` · dimension: protocol-fidelity · upheld 2/2
- Evidence: client.rs:96-101: `other => ProtocolError { code: -32603, message: format!("Codex App Server request handler failed for method '{method}'"), data: Some(Value::String(other.to_string())) }`. Upstream _internal/shared.ts runHandler -> errors.ts fromAppServerError -> `CodexAppServerRequestError.internalError(message, undefined, {method, operation: 'handle-request', cause})`, so the wire error carries no data and the cause stays local. The Rust version sends the Display text of the AppServerError to the peer, which can include transport detail. This is not listed in the Deviations table, and the schema.rs masking rule exists specifically to keep rejected values out of errors.
- Fix: Set `data: None` for the non-Request branch to match upstream, keep the detail only in logs or a local field, or add a Deviations row if the leak is deliberate.

### [low] Invalid-params wire message and data differ from upstream
- `crates/codex-app-server/src/client.rs:` · dimension: protocol-fidelity · upheld 2/2
- Evidence: client.rs:326-331 `fn invalid_params(detail: String) -> ProtocolError { code: -32602, message: format!("Invalid params: {detail}"), data: None }`, used for incoming server-request params (client.rs:92) and for response validation (client.rs:108). Upstream _internal/shared.ts decodeOptionalPayload/encodeOptionalPayload -> errors.ts CodexAppServerRequestError.invalidPayload(method, 'decode-payload' | 'encode-payload', cause) yields code -32602, message `Invalid payload for method '<method>' during '<operation>'`, and data = {issueCount, issueKinds, maximumPathDepth}. The message is visible to the peer. The Deviations table covers the local diagnostic metadata but not this wire message.

### [low] Child process group not killed when the leader exits before drop/shutdown (orphaned descendants survive)
- `crates/codex-app-server/src/client.rs:211` · dimension: safety-and-lifecycle · upheld 2/2
- Evidence: Child wait task does `child_pid.store(0, Ordering::Release);` after `child.wait()` returns (line 211). Drop (lines 336-339) and shutdown (lines 281-285, 293-297) only signal the group when `child_pid.load()` is nonzero, so once the leader has exited, `kill(-pgid, SIGKILL/SIGTERM)` is never sent even though the process group (created via process_group(0), line 178) may still contain live descendants. Reproduced with a throwaway probe: `sh -c 'sleep 300 & echo $! > pidfile; sleep 0.3'` -> after leader exit and Client drop, background pid still alive=true. Control with a live leader (`sh -c 'sleep 300 & ...; sleep 300'`) -> background pid killed on drop (alive=false). Upstream kills only the direct child via the Effect scope, so this leak is specific to the Turin group-kill deviation, which the Deviations row claims is handled.
- Fix: Keep the process-group id separately from the liveness flag: record pgid = pid once at spawn (it is never reused while any group member lives) and always issue `kill(-pgid, ...)` in Drop/shutdown, or send group SIGKILL from the wait task right after reaping the leader; do not zero the pgid on exit. Add a test mirroring the orphan-after-exit probe.

### [low] Non-UTF-8 bytes in stdout kill the whole session; upstream decodes lossily
- `crates/codex-app-server/src/protocol.rs:311` · dimension: safety-and-lifecycle · upheld 2/2
- Evidence: Read loop `Err(error) => read_state.fail(AppServerError::Transport { operation: "read-input-stream", detail: error.to_string() })` (lines 311-317) is hit because tokio `BufReader::lines()` rejects invalid UTF-8. Probe: a valid JSON notification whose string contains byte 0xff, then a request -> `Ok(Err(Transport { operation: "read-input-stream", detail: "stream did not contain valid UTF-8" }))`. Upstream protocol.ts:398 uses `Stream.decodeText()`, which is `new TextDecoder(encoding)` in non-fatal mode (apps/server/node_modules/effect/src/Stream.ts:17473), so it substitutes U+FFFD and keeps the session alive. This divergence is not recorded in the PORTING.md Deviations table. Real codex output is normally valid UTF-8, so impact is limited.
- Fix: Read raw bytes per line (e.g. split on b'\n' with read_until) and decode with String::from_utf8_lossy, stripping a trailing '\r', to match Stream.decodeText; or add a Deviations row if the strict behaviour is intentional.
