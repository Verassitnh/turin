# QC wf_e8a1a7c1-d53 — T21 hooks

Reviewer: Claude Opus 5.5 QC workflow (dimension reviewers, 2 skeptics per finding).
Confirmed: 18 · refuted: 3

## Lead report

1. HIGH: crates/hooks/src/config.rs:250-255 and 105-121, plus runner.rs:593-676 (watcher/reload_config)
   Problem: `HookPaths::for_project` always loads `<project>/.turin/hooks.toml`, and `HooksConfig::load` turns on every hook in it whenever the file exists. Nothing checks trust or consent, and nothing records an approval. A cloned repo therefore gets arbitrary `/bin/sh -c` execution on the first `thread.created` or `turn.*` event. Hot reload makes it worse: anything that later writes the file runs right away, unsandboxed, with Turin's full env, outside provider approvals. That includes an agent in workspace-write or acceptEdits mode, a `git pull`, or a branch checkout. This was reproduced (a `touch pwned` hook ran). Upstream only runs scripts the user configured or explicitly imported into settings: `resolveProjectScripts` in projectScripts.ts, and `t3.json` is import-only. Repo contents never execute on their own.
   Required fix:
   - Gate project hooks behind per-project trust stored outside the repo, e.g. `~/.turin/trusted-hooks.json` mapping canonical project root to the SHA-256 of the exact hooks.toml bytes.
   - Until the hash matches, load project hooks as inert/pending, do not run them, and report a distinct "project hooks not trusted / changed" status or error the UI can act on.
   - Re-check the hash on every reload. If it changed, drop the project hooks (keep global ones) and require re-approval.
   - Global `~/.turin/hooks.toml` stays trusted.
   - Add tests for untrusted, trusted, and edited-after-trust.
   - Document the trust model in docs/hooks.md and add a PORTING.md Deviations row.

2. HIGH: crates/hooks/src/runner.rs:400-402, 423-424, 443-458, 466-472
   Problem: `ChildGroupGuard::kill_group` gets the pgid from `Child::id()`, and tokio returns `None` for that once `wait()` has reaped `/bin/sh`. `wait()` runs inside `tokio::join!` with the pipe readers. So when sh exits while a background job still holds stdout (e.g. `cmd & ...; exit 0`), the timeout path and the Drop/shutdown path both skip `kill_process_group`, and the grandchildren survive. This was reproduced for both timeout and shutdown. In the same case a hook that exited 0 is reported as `timed_out`/`exit=None`, and a blocking `thread.created` hook holds up thread creation for the full timeout (default 300s). This breaks PORTING.md:95, the brief, and docs/hooks.md:90-92. The existing test `timeout_kills_child_and_grandchild` misses it because its command ends in `wait`, which keeps sh alive.
   Required fix:
   - Record the pid right after `spawn()` (it is the pgid because of `process_group(0)`) as `pgid: Option<u32>` in the guard.
   - Always send `kill(-pgid, SIGKILL)` with it on timeout and in Drop, whether or not the leader has been reaped.
   - Add regression tests where sh exits before its background child, covering both the timeout path and the shutdown path.
   - Consider returning once sh exits plus a short drain, rather than blocking on pipe EOF until timeout. At minimum, keep the real exit code.

3. MEDIUM: crates/hooks/src/runner.rs:618-632 (`start_watcher`)
   Problem: The watcher only watches a config file's parent directory if it exists at construction. It returns early when none do, and never re-arms. A project with no `.turin/` is the normal starting state, so creating `.turin/hooks.toml` later (or `~/.turin/`) is ignored until restart. Deleting and recreating a watched `.turin/` also loses the watch. This contradicts docs/hooks.md:16-18, and was reproduced.
   Required fix:
   - Watch the nearest existing ancestor non-recursively (the project root, and `$HOME` or TURIN_HOME's parent), and add the `.turin` watch once that directory appears.
   - Alternatively, check the mtime/existence of the config files on each dispatch.
   - Any fix here must go through the trust gate in item 1.
   - Add a test that starts with no `.turin` directory.

4. MEDIUM: crates/hooks/src/runner.rs:572-591 (`try_spawn`, line 583)
   Problem: The JoinSet is only joined in `shutdown()` (L565), so every finished non-blocking hook task stays in the set. Measured: 200 runs gave `len=201`, with each future about 34 KB because of the two 16 KB stack `chunk` buffers in `read_bounded` (L348). Memory grows without bound in a long session, and hook-task panics are never seen.
   Required fix:
   - In `try_spawn`, before `set.spawn`, reap finished tasks: `while let Some(r) = set.try_join_next() { if let Err(e) = r { if e.is_panic() { tracing::error!(..) } } }`.
   - Optionally move the read buffers to the heap.
   - Add a test asserting `len()` stays bounded after many runs.

5. LOW: crates/hooks/src/runner.rs:259
   Problem: The comment says the env is "Login-shell-equivalent", but hooks only inherit the bare parent env plus TURIN_*. No crate hydrates PATH: there is no port of upstream's `fixPath`/`readEnvironmentFromLoginShell`/`mergePathEntries`/launchctl fallback. A Finder-launched app would give hooks `/usr/bin:/bin`, so `gh`, `npm`, `bun` and similar fail with exit 127. Upstream does this hydration once at process startup, not in the runner.
   Required fix:
   - Correct the comment to say the hook inherits the parent env and relies on PATH hydration at app startup.
   - Add a PORTING.md Deviations or tracked-task entry for porting shell.ts/os-jank `fixPath` into turin-shared and calling it at app startup.
   - Do not add per-hook hydration in this crate.

6. LOW: crates/hooks/src/config.rs:278-284 (`paths_match`, used from runner.rs:645)
   Problem: The fallback compares `canonicalize` on both sides, and that fails once the file is deleted. FSEvents reports canonical paths (`/private/var/...`), so deleting a config under a symlinked path (macOS `/tmp`, `/var`, or a symlinked project root or TURIN_HOME) never triggers a reload, and the deleted hooks keep running. Reproduced: 1 hook before the delete, still 1 after.
   Required fix:
   - At watcher setup, canonicalize each config file's parent directory once and compare event paths against `canonical_parent.join(file_name)`.
   - Add a delete test that uses a non-canonical path.

7. LOW: docs/hooks.md:3-6 and 99-115 (comment at line 113)
   Problem: The docs say hooks let you "recreate" the launch-into-worktree flow, and that the "worktree path come[s] from the env". In fact the script invents `../wt/$TURIN_THREAD_ID`. `TURIN_WORKTREE_PATH` is only set when `thread_cwd` already exists (runner.rs:128-130), and `HookRunResult`/`DispatchSummary` give the hook no way to report a path back. Turin never learns about the new worktree, so the agent and later `cwd = "thread"` hooks still run in the project root.
   Required fix:
   - Reword the intro and the example so they no longer claim the worktree flow is reproduced, and remove the "worktree path comes from the env" comment.
   - Or define and document a return protocol for blocking `thread.created` hooks (e.g. a JSON line on stdout carrying `worktreePath`), with a PORTING.md note.

8. LOW (optional hardening; reviewers split 1 of 2): crates/hooks/src/runner.rs:256-262, together with 127-132
   Problem: Inherited `TURIN_*` vars are not scrubbed. Since `TURIN_THREAD_ID` and `TURIN_WORKTREE_PATH` are only set when present, stale inherited values can leak into thread-less events. Upstream's `createTerminalSpawnEnv` strips `T3CODE_*` and `VITE_*` from script environments. Turin has no `TURIN_*` secrets today, so the current impact is minimal.
   Required fix: Before setting fresh values, call `env_remove` for every inherited key with the `TURIN_` prefix.

Verdict: FAIL. There are 2 high findings: project hooks run with no trust gate (including on hot reload), and the process group is not killed once the shell leader has been reaped.

## Confirmed findings (raw)

### [high] A cloned repo's .turin/hooks.toml runs arbitrary commands with no opt-in or trust step
- `crates/hooks/src/config.rs:253` · dimension: spec · upheld 2/2
- Evidence: `HookPaths::for_project` always adds `project_root.join(".turin").join("hooks.toml")`, and `HooksConfig::load` (config.rs:105-121) parses and enables it whenever `path.is_file()`. Nothing checks trust, asks for consent, or records an approval. Upstream never runs commands taken from repo files: `resolveProjectScripts` (packages/shared/src/projectScripts.ts) reads scripts only from server settings or the project aggregate the user set in the UI. The only repo file upstream reads is VcsProjectConfig, which gives the VCS kind and nothing executable. Verified with a throwaway program in /tmp/t21qc: a directory containing `.turin/hooks.toml` with `event="turn.started" command="touch pwned"`, opened via `HookRunner::for_project`, created `pwned` on the first dispatch (printed `repo-supplied hook executed: true`). Any repo the user clones and opens in Turin gets code execution on the first thread or turn event.
- Fix: Gate project hooks behind explicit per-project trust, stored outside the repo in Turin settings or the DB. Bind the trust to a hash of the file content so later edits (a `git pull`, or the agent itself writing `.turin/hooks.toml`) need re-approval. Hot reload must re-check this too. Until the user approves, load project hooks as pending and report them on the channel, but do not run them. Document the trust model in docs/hooks.md and add a PORTING.md Deviations row.

### [high] A timeout or shutdown after /bin/sh has exited does not kill the process group, so grandchildren survive
- `crates/hooks/src/runner.rs:450` · dimension: spec · upheld 2/2
- Evidence: `kill_group` calls `self.id()`, which is `Child::id()` (runner.rs:400-402). Tokio returns None for that once `wait()` has reaped the child. `run()` joins `wait` with both pipe readers (runner.rs:423-424). So when sh exits but a background job still holds stdout open, `wait` finishes first and the pid becomes None. The timeout branch (runner.rs:315) and `Drop` on task abort (runner.rs:467-472) then skip `kill_process_group`, and `start_kill` on an already-reaped child does nothing. Verified with /tmp/t21qc: hook `sleep 60 & echo $! > gc.pid; exit 0`, blocking=true, timeout_secs=1 gave `timed_out=true ... grandchild_alive_after_timeout=true`. The spec says "timeout kills the whole process group". docs/hooks.md:90-92 says background jobs "cannot outlive it". Neither holds.
- Fix: Store the pid/pgid in `ChildGroupGuard` at spawn time, before any wait. Always `kill(-pgid, SIGKILL)` on timeout or Drop: the group outlives its leader while members remain, so this still works after the leader is reaped. Add a test where the shell exits and a background job keeps stdout open.

### [low] Finished background hook tasks pile up in the JoinSet until shutdown
- `crates/hooks/src/runner.rs:583` · dimension: spec · upheld 2/2
- Evidence: `try_spawn` calls `set.spawn(future)` on the shared `JoinSet` (runner.rs:580-584). Nothing calls `join_next`/`try_join_next` except `shutdown()` (runner.rs:565). A tokio JoinSet keeps each finished task's slot until it is joined. In a long-running app, every non-blocking hook run (turn.started/completed fire on every turn) leaves an entry, so memory grows without bound. Panics inside a hook task are also never observed. The brief asks for a JoinSet that is "drained"; here it is drained only at shutdown.
- Fix: Reap finished tasks opportunistically: call `while let Some(r) = set.try_join_next() { log a panic in r }` inside `try_spawn` before spawning. Or run a reaper task that does the same.

### [high] Process group is not killed on timeout or shutdown once the shell has exited, so backgrounded grandchildren survive. The hook is also reported as timed_out even though it exited 0.
- `crates/hooks/src/runner.rs:450` · dimension: correctness · upheld 2/2

### [medium] Hot reload never starts when the config directory does not exist at construction
- `crates/hooks/src/runner.rs:618` · dimension: process · upheld 2/2
- Evidence: start_watcher only watches a parent that exists: `if let Some(parent) = path.parent() && parent.is_dir() ...` (L618-620). If neither dir exists, it returns early at `if watched.is_empty() { return; }` (L630-631), and nothing retries later. Most projects have no `<project>/.turin/` directory when Turin first opens them, and often ~/.turin does not exist either. Creating `.turin/hooks.toml` afterwards is never picked up, despite docs/hooks.md L16-17 ("Files are watched for changes and reloaded automatically"). Reproduced in a /tmp copy: `HookRunner::for_project(tmp)`, then write `<tmp>/.turin/hooks.toml`. After 3s of polling, the test failed with "project hooks.toml created after startup never hot-reloaded".
- Fix: Watch the nearest existing ancestor instead (the project root for `.turin/hooks.toml`, and $HOME for `~/.turin`). Match on the config file path, and add the `.turin` dir watch once it appears. Or document that reload() is required in that case, and have the app call it. Add a test for a config created after startup.
