## Confirmed findings (raw)

### [low] KeyedLock keeps idle keys when a waiter is cancelled
- `crates/projects/src/keyed_lock.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: lock() increments entry.users under the mutex (lines ~48-53) and then awaits semaphore.acquire_owned(). The guard that would call release() only exists after the await. If the future is dropped while waiting (for example a timeout or client disconnect), users is never decremented, so the entry stays in the map. The module doc says 'A key's lock exists only while someone holds or waits on it'. Verified with a scratch copy of keyed_lock.rs: hold key 'a', time out a second lock('a') waiter, release the holder. active_keys() still returns ["a"] with nothing holding or waiting. Mutual exclusion is unaffected, so this is a bounded memory leak that breaks the documented invariant.
- Fix: Make the waiter's registration cancellation-safe: use a drop guard created right after users += 1 that decrements users (and removes the entry when it reaches zero) unless the guard is disarmed after the permit is taken. Or take the permit through a helper that owns the decrement on drop. Add a test that cancels a waiter and asserts active_keys() is empty after the holder releases.

### [low] Unselected number tokens are buffered without any cap or budget charge
- `crates/projects/src/agent_session_json.rs:268` · dimension: safety · upheld 2/2
- Evidence: Lex::Num branch: `number.buf.push(byte); self.lex = Lex::Num(number);` runs for every digit whether or not the value is selected (NumberToken created at line 362 with `buf: vec![byte]`). Only enter_value charges a flat 64 bytes (line 405). finish_value (line ~466) never reserves for numbers, unlike end_string (line 450 `self.reserve(string.raw.len() * 2)`). Import admits transcripts up to MAX_IMPORTED_TRANSCRIPT_BYTES = 4 GiB (agent_session_discovery.rs, const block), so one record whose unselected field is a multi-GiB digit run allocates that whole run outside the 32 MiB history budget. PORTING.md line 309 says 'unselected values cost nothing ... the budget still bounds retained data', which is false for this path. Upstream AgentSessionJson.ts `assemble` calls reserve(64 + token.value.length * 2) on every streamed token, so retention is bounded there.
- Fix: Charge number bytes as they are pushed (reserve per byte or per chunk, as upstream does), or reject a number token above a fixed length cap and treat it as a malformed record. Then correct the PORTING.md Deviations row for AgentSessionJson.ts to match the real behaviour.

### [low] Selected string tokens are fully buffered before the history budget is checked
- `crates/projects/src/agent_session_json.rs:228` · dimension: safety · upheld 2/2
- Evidence: Captured string bytes are pushed unchecked into `string.raw` (push sites at lines 228, 242, 251, 258). The only reserve for a string is in end_string: `if string.capture { self.reserve(string.raw.len() * 2)?; }` (line 450). The 32 MiB MAX_IMPORT_HISTORY_BYTES budget therefore fires only after the whole token is in memory, so a selected string field of hundreds of MB to 4 GiB is held in full before rejection. Upstream reserves per stringChunk as it streams (AgentSessionJson.ts assemble, reserve(64 + value.length * 2) per token).
- Fix: Call self.reserve(bytes) as each byte or chunk is pushed into string.raw (or check raw.len() against the remaining budget at each push) so the budget rejects oversized selected strings while streaming.

### [low] Symlinked transcripts and project directories are followed outside the scanner roots
- `crates/projects/src/agent_session_discovery.rs:803` · dimension: safety · upheld 2/2
- Evidence: stat_transcript (line 803-808) calls `self.fs.stat(file_path)`, which is tokio::fs::metadata and follows symlinks, then accepts it when `stats.is_file`. Reads go through `self.fs.open(...)` (lines 574 and 636, tokio::fs::File::open, also symlink-following). discover_claude_transcripts (~line 680-720) walks `projects/<dir>` via read_dir, which follows a symlinked directory. Nothing compares the realpath with the home root. A `~/.claude/projects/x/y.jsonl` symlink to any readable JSONL file is parsed, and its cwd and messages become importable threads. This breaks the brief's 'never follow paths outside its roots' rule. Upstream does the same (fileSystem.stat in AgentSessionScanner.ts), and PORTING.md has no Deviations row for it.
- Fix: Use symlink_metadata (lstat) and skip symlink entries, or canonicalize each candidate and require it to remain under the canonical home root (`real_path` is already on the trait). Record the choice as a Deviation if it differs from upstream.

### [low] In-flight lookups re-insert values after invalidation, so stale identities are cached
- `crates/projects/src/project_enrichment_service.rs:302` · dimension: safety · upheld 2/2
- Evidence: repository_identity: `let identity = self.identity_source.resolve(workspace_root).await; self.identity_cache.insert(key, identity.clone(), self.success_ttl);` (lines 302-304). favicon() does the same at 314-324. invalidate() (lines 228-237) removes entries. A lookup that started before invalidate() re-inserts its pre-invalidation result for the full success TTL. Same pattern in repository_identity_resolver.rs lines 123-129 (repository_roots) and 136-141 (identities). Upstream Cache.ts (~lines 640-660) does not do this: an invalidated entry is no longer in the map, and completion only sets expiresAt on the detached entry. Failure: project A at /repo/a starts an identity lookup; A is deleted (ProjectService invalidates /repo/a); project B is created at /repo/a with a different origin; A's lookup completes and writes the old identity; peek() returns it for the success TTL. PORTING.md line 311 logs only the missing single-flight, and says results are equal.
- Fix: Keep a per-key generation (or epoch) in TtlCache. invalidate() bumps it, and insert() only stores the value when the generation read before the lookup still matches. Log the change as a Deviation or fix it to match upstream.

### [low] Whole-file reads of .git pointer and config have no size cap or type check
- `crates/projects/src/agent_session_discovery.rs:526` · dimension: safety · upheld 2/2
- Evidence: read_git_identity: `self.fs.read_file_string(&git_path)` (line 526, when `.git` is not a directory) and `self.fs.read_file_string(&join(&[&git_dir, "config"]))` (line 544). LocalScannerFileSystem::read_file_string (line 141-143) is `tokio::fs::read_to_string(path).await.ok()`, with no is_file check and no size limit. A `.git` FIFO or a multi-GiB file under a cwd named in a transcript is read in full, and a FIFO blocks a blocking-pool thread forever so the scan never completes. The same unbounded pattern appears in project_favicon_resolver.rs:426 (`tokio::fs::read(&source_path.absolute_path)`), and in read_directory (agent_session_discovery.rs:130-141), which collects every entry name while the budget counts only one operation per directory call. Upstream has the same behaviour (readFileString in AgentSessionScanner.ts), so this is a parity gap with the brief's 'bounded' rule, not a regression.
- Fix: stat the path first and require is_file, then read through a bounded reader (for example 64 KiB for config and the gitdir pointer). Cap the entries kept per read_dir or charge entries against the operation budget.
