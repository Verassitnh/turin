## Confirmed findings (raw)

### [low] expand_home_path joins an absolute suffix and widens managed worktree roots
- `crates/review/src/worktrees_directory.rs:` · dimension: logic-fidelity · upheld 2/2
- Evidence: Line 54: `return normalize_lexical(&Path::new(home).join(rest))` where `rest` is the text after `~/` or `~\`. Upstream provider-core expandHomePath uses `NodePath.join(home, value.slice(2))`. For setting `~//etc`, Node gives `/home/u/etc` (verified with node), while Rust `Path::join` with an absolute argument replaces the base and yields `/etc` (verified with a rustc probe). `resolve_worktrees_directory` (line 77-85) then accepts `/etc` as a managed worktrees root, so `assert_workspace_bound_cwd` in review_service.rs:175-192 accepts any cwd under /etc as a review cwd. This breaks the containment the review reads depend on. The same applies to previousWorktreesDirectories entries.
- Fix: Join by concatenation, not Path::join, to match Node: strip the leading separators from `rest` (or join the string form, e.g. `format!("{home}/{rest}")` then normalize_lexical), so an absolute-looking suffix stays under home. Add a unit test asserting `expand_home_path("~//etc", "/home/u") == "/home/u/etc"` and that resolve_worktrees_directory("~//etc", ...) is under home.

### [medium] Workspace containment bypass: lexical '..' folding before realpath, but raw cwd is passed to git
- `crates/review/src/review_service.rs:232` · dimension: safety · upheld 2/2
- Evidence: review_service.rs:232-233 `let resolved = normalize_lexical(&absolute); match std::fs::canonicalize(&resolved)` folds `..` lexically before resolving symlinks. The validated value is discarded: review_service.rs:113 `self.vcs.detect_kind(input.cwd.as_str())`, :134 `self.git.get_review_diff_preview(input)` and :149/:163 use the raw `input.cwd`. The git driver spawns with that raw string: crates/git/src/git_vcs_driver_core.rs:739-740 `run.cwd = Some(input.cwd.clone()); run.spawn_cwd = Some(input.cwd.clone());`, and driver_rest.rs:373 resolves repository paths from the raw cwd. Reproduced with a scratch layout: ws/link -> outside/inner (a git repo at outside/). Lexically `ws/link/..` normalizes to `ws`, which is inside the workspace, so the check passes. The kernel resolves `ws/link/..` to `outside/`. `git -C <ws>/link/.. rev-parse --show-toplevel` returned `<outside>` and `cat <toplevel>/secret.txt` printed the file. getDiffFileContents then reads files from the outside repo (driver_rest.rs:549 `read_working_tree_review_file` uses that toplevel). A repository cloned into a workspace can commit such a symlink. The same lexical-first logic also accepts non-existent paths under a symlinked ancestor (line 235 returns the lexical form on NotFound). Existing tests (review_service.rs:427-614) do not cover `..` after a symlink. Upstream has the same flaw: upstream/apps/server/src/review/ReviewService.ts:48-50 uses `path.resolve` then `realPath`, and :130/:168 pass the raw `input.cwd`. It is not in the Deviations table, which PORTING rule 4 requires for fixed bugs.
- Fix: Canonicalize the cwd once and use the canonical PathBuf for every downstream call (detect_kind, git driver input). Resolve symlinks before any `..` folding, e.g. canonicalize the nearest existing ancestor and then re-append the remaining components lexically. Add a test where a workspace symlink is followed by `..` and assert rejection. Log the fix in the Deviations table.

### [low] Unvalidated base_ref reaches git argv, allowing option injection (git show --output writes files)
- `crates/git/src/git_vcs_driver_core/driver_rest.rs:532` · dimension: safety · upheld 2/2
- Evidence: driver_rest.rs:532 `argv(&["show", &format!("{old_revision}:{}", input.old_path.as_str())])`, where old_revision is `input.base_ref` for the working-tree source (driver_rest.rs:512-517). base_ref is only `TrimmedNonEmptyString` (crates/contracts/src/review.rs:97-101), with no check for a leading '-'. Same pattern at driver_rest.rs:213 `argv(&["merge-base", &base_ref, "HEAD"])` with an explicit base_ref and no `--end-of-options`. Reproduced: `git show "--output=<dir>/written:file.ts"` created `<dir>/written:file.ts` containing the blob, i.e. an arbitrary file write with object content at an attacker-chosen path. `git merge-base --fork-point HEAD` also runs with the injected option. Upstream builds the same argv (upstream/apps/server/src/vcs/GitVcsDriverCore.ts:3017-3020), so this is a faithful port of an upstream weakness that PORTING rule 4 says to fix and log.
- Fix: Reject base_ref (and head_ref/explicit refs) starting with '-' in ReviewService before dispatch, or validate with `git check-ref-format`. Also pass `--end-of-options` before the revision where git supports it. Record the deviation.

### [low] Synchronous filesystem IO on async paths during containment checks and file reads
- `crates/review/src/review_service.rs:233` · dimension: safety · upheld 1/2
- Evidence: review_service.rs:230-233 `canonicalize_path` calls blocking `std::path::absolute` and `std::fs::canonicalize`. It is called from the `async fn assert_workspace_bound_cwd` at :176, :177, :183 (per managed root) and :204 (per project root), so each review request runs blocking realpath calls on tokio worker threads. The same pattern is in the git driver: crates/git/src/git_vcs_driver_core/driver_rest.rs:575 and :584 (`std::fs::canonicalize`), :604 (`std::fs::metadata`) and :632 (`std::fs::read`) inside `async fn read_working_tree_review_file`. A stalled network mount (SMB/NFS workspace) can block a worker thread for an unbounded time. PORTING.md requires tokio for backend work.
- Fix: Move the canonicalization and metadata/read calls into `tokio::task::spawn_blocking` (or use tokio::fs), so the async runtime does not block on filesystem IO.
